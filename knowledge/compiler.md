# The Smith compiler

Smith's compiler is an optimizing compiler built around `for` expressions. Its optimizations are fixed rules keyed on shape and structure, with no search and no heuristics that vary between builds, so performance is predictable and builds stay fast. It emits machine code and GPU shaders itself, with no LLVM.

## How `for` is compiled

Every [`for`](language/for.md), element-wise operator, reduction, and `@` is lowered to the kernel form and leaves it as loops of the [scalar form](#scalar-form). There is no other way from a `for` to code, so nothing built for arrays is replaced when a pass is added: a pass is one more step between the two.

### The kernel form

The kernel form holds a computation over arrays as nests. A nest has three parts.

- **An index space:** the indices of the nest, in order, each with its size, which is a constant, a size parameter, or the size of an array it reads.
- **A body:** code of the scalar form that gives the value at one point of the index space. It reads an element of an array by its indices, and may read the value another nest gives at a point.
- **What is done with the values:** kept as an array of the shape of the index space, or reduced along some of the indices by an operation with a starting value, as `sum` does with `+` and 0.

A reduction is a part of the nest and not a loop that happens to add, so a pass that regroups it, splits it between lanes, or shares it between cores reads what it is and does not have to find it. A read of another nest's value is a part of the body, so putting one nest into another is putting its body where it is read, with its indices for the reader's.

### What is built first

`for` is built first with no pass at all: each nest becomes one loop for each index, in the order written, each array a nest gives is kept in memory, and each reduction adds in order. That is correct and slow. Each pass after it is measured against the same loops written in C and built with `-O3`, with the time to build beside the time to run.

### The passes, in the order they are built

- **Fusion.** An array read once per element fuses into its consumer. An array read repeatedly, or by several consumers, gets a buffer.
- **Whole-function vectorization.** A scalar function called inside a `for` runs across SIMD lanes or GPU threads, with branches turned into masks.
- **Reductions.** Each core runs several SIMD accumulators, cores combine their partial results, and a GPU uses a tree. The grouping is fixed for a given compiler and target and never depends on thread count, so results are repeatable. A reduction that fills one element of an array runs in order along its index.
- **Contractions.** A `for` with a `sum` over a shared index, which is what every `@` expands to, is recognized and compiled as a tuned library would write it: loop order chosen, blocked for the cache, with a vector kernel inside.
- **Strategy by size.** Type parameters are always specialized. For size parameters, a shared version always exists that takes the sizes at run time and picks its strategy with a size check: a simple loop, or cache blocking and threads. A specialized copy is made only when the sizes are constants and the operation count at those sizes is under a fixed bound, as for a 4 by 4 matrix, which is then fully unrolled into SIMD registers. The rule uses no profile data, and `smith cost` reports which version a call uses.
- **Layout.** No address is observable, so the compiler is free to store an array of structs as one array per field.
- **Devices.** Inside `with device(gpu)`, each fused loop nest becomes a GPU kernel.

None is built. Each is one step over the kernel form, and the nests that leave it are the nests the next reads.

## Scalar form

Below the kernel form, every program is scalar code in one small typed form, which is the same for every target. A feature of the language is lowered to it once, and no target's code changes when a feature is added. The compiler's own code and the edges of a server are scalar from the start, and a kernel reaches this form as explicit vector operations.

- **Every value is named once.** A function is a list of blocks. A block takes parameters, runs its instructions in order, and ends by jumping to a block with arguments, by choosing between blocks, or by returning values. An instruction gives a value that never changes, which is the form known as SSA, and a block's parameters are how values meet where paths join.
- **Every value has a type and a size:** an integer of 8, 16, 32, or 64 bits, a float of 32 or 64 bits, an address, or a vector of a fixed number of one of those. Whether an integer is signed belongs to the operation, not to the value. Floats of 16 bits are not built yet.
- **An operation says whether its answer fitted.** `Overflows` is one instruction with the operation as a field, `Add`, `Sub`, or `Mul`, and whether the numbers are read as signed or as unsigned. It gives two values, the number with the bits that do not fit left off, which is what the `Binary` instruction gives, and an integer of 8 bits that is 1 when the number is not what the operation gives of the two numbers, and 0 when it is. The evaluator works it out in 128 bits, so every target is held to what the checked functions give. A target makes the flag the flags of the operation when the value is read by the choice that follows it or by the end of its block alone, and a value in a register otherwise. On x86-64 a number of 64 bits is `add`, `sub`, or `imul` with the carry, or the overflow when signed, and an unsigned product is `mul` with its carry; a narrower number is widened, worked out in 64 bits, and looked at, for unsigned numbers for a bit above its size and for signed numbers for what its low bytes, extended, differ from. On arm64 a number of 64 bits is `adds` or `subs` with the carry, the borrow, or the overflow, and a product is `mul` with `umulh` or `smulh` and a compare of the high half with 0 or with the sign of the low half; a narrower number is looked at as on x86-64.
- **A division is given a divisor it may take, and is run only where the source ran it.** `DivU`, `DivS`, `RemU`, and `RemS` are `Binary` operations, the quotient and what is left over of two integers of one size, read as unsigned and as signed numbers, both rounding toward zero, so that what is left over has the sign of the first and `(a / b) * b + a % b` is `a`. An instruction is given a divisor that is not zero and, for the signed ones, a first number that is not the least of the size when the divisor is -1, whose quotient the size cannot hold: the checker of the language proves the first and keeps a result at the size of its exact range, so no instruction tests either, and a processor that is given one faults (`div` of x86-64, `div_s` of WebAssembly) or gives a number of its own (`udiv` and `sdiv` of arm64), so what a program does that gives one is not defined. The evaluator ends the run, with a message that names the instruction, when it is given one, and folding leaves a division that is given one as it is. The well-formedness check does not look at values, as a pass may leave a division by a constant zero in a block that nothing reaches until the next walk takes it away. No pass runs a division where the source would not have run it: none moves an instruction to a path the source did not take, and a test runs divisions that a condition guards, with the numbers that the condition excludes, through each pass and every target.
- **Nothing is a group.** A struct or a tuple is its parts, each a value of its own, and so is an array of a size written as a number, which is the scalars of its elements one after another. A text is an address and a length. An enum is the number of the case it holds, in one byte, and then places that its cases share by type. For each scalar type the enum has as many places of that type as the case that needs the most of them, so an enum whose cases each hold one text has one address and one length, however many cases it has. A case's parts are split into scalars in the order written, and the k-th scalar of a type goes to the k-th place of that type. The types are taken in the order they first appear among the cases' scalars, cases in order, so `Option[str]` is a case number, an address, and a length, and an enum with a case that holds a `bool` and a case that holds a text is a case number, a byte, an address, and a length. A place that the case a value holds does not use holds the zero of its type, and nothing reads it. No address is observable in Smith, so nothing forces a value into memory, and a struct lives in registers like any other values. Memory is for what has a size known only at run time, such as an array's elements, and is read and written through an address at the element's real size.
- **The instructions are few:** constants, arithmetic, bit operations, shifts, and comparison at each width, arithmetic that says whether its answer fitted, widening and narrowing, a choice between two values, a read and a write through an address, the address of bytes of the function's own frame, a call of a function, which may give back several values, and a call into the system.
- **An array that is read or assigned at an index the program works out is kept in the frame, and every other is its scalars.** `Frame { bytes }` gives the address of `bytes` bytes of the function's frame: the same bytes each time it runs in one run of the function, bytes that no other `Frame` shares, holding nothing until stored to, and gone when the function returns. It is never made one instruction of two, never merged with another, and no address of it is given away: an array that is passed, returned, or held by another value is loaded into its scalars first, so it is copied and no name sees another's writes. A name whose array is indexed at anything but a number written out, or assigned so, in the function where it is defined, is given a `Frame` of the size of its elements laid out as the elements of a list are, written when the name is defined and whenever it is assigned whole, so `a[i]` is one load at the address of the element and `a[i] = e` is one store, and an array used whole is its elements loaded, once for each use. A `loop` over an array, and an array taken where a `List` is, write the array to a `Frame` once and are the list that is there, with its size and its room the size of the array. An array written out, `[1, 2, 3]`, holds each item at the type of the elements of the array, which is the range of all its items: an item is typed by what it is written as and is held as an element is, so `xs[0]` of that array is a number of 8 bits where `repr` takes one of 8, and the form is well formed at the call. An array that is not a name, and one that is a field, is written to a `Frame` for each index that is not a number, which costs its size in stores. A function that calls itself where the call is not the last thing it does is one loop with one frame for all its calls, so what it asks of `Frame` it asks of the system instead, as the memory of each call. x86-64 and arm64 put the bytes of each `Frame` in the frame of the function after the places of its values, at a multiple of 16. WebAssembly takes them from a stack of 1 MiB in the linear memory, before the memory the program asks for, that a global points to, which a function with a `Frame` moves on by its bytes when it begins and back when it returns, and a function that would move it past the end of the stack ends the program with status 1; a module whose program has no `Frame` has neither the stack nor the global.
- **A float is a value like any other, and no instruction of floats is rewritten.** The instructions are a constant, which holds the bits of the number, `+`, `-`, `*`, and `/` of two floats of one size, negation, the square root, the rounding of a float to a whole number, the bits of a float as an integer of its size and the float of an integer's bits, the six comparisons, a float from a whole number and a whole number from a float, a float of one size from the other, and a read, a write, and a choice, which are those of any value at the float's size. Each gives what IEEE 754 gives, rounded to the nearest, ties to even, and the evaluator is held to the bits. These are what the evaluator fixes where IEEE 754 leaves a result open:
  - **A comparison** gives an integer of 8 bits. The zeros of both signs are equal, and nothing is below, above, or equal to a float that is not a number, so each comparison but `!=` is 0 when either is not a number, and `!=` is 1.
  - **A square root** is the float nearest the exact root, and the even one where it is half way, which IEEE 754 gives and every chip has as one instruction, so a root is not a function of a library: a number below 0 has none and gives the one float that is not a number, and `-0.0` gives itself. **A rounding to a whole number** gives the whole number below the float, above it, towards zero, or nearest it with the even one at a half, as a float of its size, which IEEE 754 gives exactly and every chip has as one instruction: a zero, and a float that rounds to zero, keep their sign, and a float of 2^52 or more, or 2^23 for an `f32`, is itself, as an infinity is. **The bits of a float** are an integer of its size, and **the float of bits** is the float with those bits, and each keeps every bit of a float that is not a number, as a read and a write do; they are no work for a chip but a move between a register of floats and one of integers.
  - **A whole number from a float** is the float without its fraction when that fits the type, the least or the greatest number of the type when it does not, whether signed or unsigned, and 0 when the float is not a number, so that the instruction gives something for every float on every chip. This is what the instruction of the form gives, and not the rule of the language for making a whole number of a float, which is not decided and may ask for a check first. A float from a whole number is the nearest float, read as signed or as unsigned.
  - **A result that is not a number** is one float, positive, quiet, with no payload, in the evaluator and wherever a pass folds, so that what is folded does not depend on the computer that builds it. The sign and the payload of such a result in an executable are the chip's, so a test takes any float that is not a number for any other. Negation flips the sign bit of whatever it is, and a read, a write, and a choice keep every bit.
  - **A product is fused with the one sum or difference that uses it, where the form is made.** The fused instruction works out `a * b + c`, `a * b - c`, or `c - a * b` of floats, or of each lane of vectors of floats, exactly, and rounds once, and the evaluator gives its bits by the host's fused multiply and add. Whether a product is fused is part of what the program means, so it is decided from each function as written, before any pass, by one function over the form, `fuse`, which a form is given when it is made: a product whose one read, in its own function, is as an operand of an addition or a subtraction of the same type, on either side of it, named or not, is fused with it. A product that is read twice, or by anything else, such as a jump, a call, a comparison, or another product, stays a product, and a sum of two products fuses the first. A product that a call gives back is read by the call, and not by the sum, so it is never fused with it, whether or not the call is inlined. No pass makes a fused instruction or takes one apart: they carry it as any value, folding works out one whose inputs are all constants by the evaluator's code, and removal takes away the product it leaves. So every executable gives what the evaluator gives of the form as it was made. The form is fused by `fuse` where floats are lowered from source, before any pass, and the tests that build a form apply `fuse` to the forms they build. This is what [the rules floats keep](language/float-rules.md#a-product-is-fused) say.
  - **The passes treat a float as any value.** Inlining, trimming, threading, working out the same thing once, and removal read and rename its instructions as any other. Folding replaces an instruction of floats whose inputs are all constants by a constant, worked out by the code the evaluator uses, and takes nothing else: no `x + 0.0`, `x * 1.0`, or `x - x` is rewritten, as each gives other bits for some `x`, and no product or sum is regrouped.
- **A vector is 128 bits of lanes, each an integer of 8 to 64 bits or a float of 32 or 64 bits,** so it has 16, 8, 4, or 2 lanes, and lane 0 is the lowest bits, in a register and in memory, where a vector takes 16 bytes and lies at a multiple of 16 in an element. Wider vectors and the instructions that only some chips have are not in the form. The instructions are a constant, which holds the bits of the whole, `+`, `-`, `*`, and the three bit operations of two vectors of integers, `+`, `-`, and `*` of two vectors of floats, a read and a write through an address and a choice of a whole vector, which are those of any value, and these, each of which the evaluator gives from the scalar instruction of each lane:
  - **A comparison gives a mask,** a vector of integers as wide as the lanes, each lane all ones where the comparison holds and all zeros where not: the six comparisons of two vectors of integers, read as signed or as unsigned numbers, and of two vectors of floats, which hold for a float as the scalar comparison does. **A choice by a mask** takes each bit of its result from the first value where the mask has a 1, and from the second where it has a 0, which for a mask that a comparison gave is the scalar choice on each lane.
  - **One value spread** makes every lane of a vector the integer or float, **a lane read** gives a lane as a scalar, and **a lane written** gives the vector with one lane replaced; the lane is a number in the instruction, below the number of lanes.
  - **A sum of the lanes** of integers wraps. A sum of floats adds the lanes that lie next to each other, and then those sums in pairs, so that four lanes give `(l0 + l1) + (l2 + l3)`, each addition rounding as the addition of floats does, so that every target is held to the same bits. **The place of the first lane a mask has set** is the place of the first lane whose top bit is 1, which for a mask is its first lane that is set, as an integer of 64 bits, and the number of lanes when none has.
  - **The passes treat a vector as any value.** Folding replaces an instruction of vectors whose inputs are all constants by a constant, worked out by the code the evaluator uses, and rewrites nothing else, as it does for floats: no `x + 0`, `x * 1`, or `x - x` is rewritten, and no product and sum are made one.
- **x86-64 builds floats with the instructions of SSE2, one for one, but for a fused product and a rounding to a whole number, and no instruction is made of two.** A float is held in a register of floats or in the frame. `+`, `-`, `*`, and `/` are `addss` and the other three, or the same for doubles, with the second value read from the frame where it is. A comparison is `ucomiss` or `ucomisd`, with its operands the other way round for `<` and `<=`, so that `a < b` is `b` above `a`, which is false for a float that is not a number, and then `seta` or `setae`; `==` is `sete` and `setnp` joined by `and`, and `!=` is `setne` and `setp` joined by `or`. Negation reads the float's bits into `rax`, flips the top bit with `btc`, and gives them back. A choice reads both floats' bits into `rax` and `rcx` and is a `cmov`. A float constant is its bits made in `rax` and moved, and zero is `xorps`. A float from a whole number is `cvtsi2ss` or `cvtsi2sd` of the number read as 64 bits, and for an unsigned number of 64 bits whose top bit is set, the number halved with its lowest bit kept, converted, and doubled. A whole number from a float is worked out in 64 bits from the float as a double, by `cvttsd2si`, and the least integer it gives for a float that does not fit or is not a number is told from the float itself by comparing it with 0; for an unsigned number and for a size below 64 bits it is then held to the greatest number and the least. So the instruction that saturates costs, on this chip, whose own conversion does not: for a signed number of 64 bits that fits, 4 instructions, which are the float moved to `xmm15`, `cvttsd2si`, a compare of the result with 1, and the branch on overflow, which is taken for every result but the least integer; 6 more for a size below 64 bits, which is two compares and two `cmov`s with their constants; 9 for an unsigned number of a float below 2^63, and 12 above it; and about 6 more for a float that is not below the least integer, since only then is the float itself looked at. A float of one size from the other is `cvtss2sd` or `cvtsd2ss`. A rounding to a whole number is `roundss` or `roundsd` of SSE4.1, which the level `x86-64-v3` holds, with the way to round in its immediate and the bit set that keeps an inexact result from being signalled. A fused product is `vfmadd231ss`, `vfmsub231ss`, or `vfnmadd231ss`, or the same for doubles, of FMA, the one instruction above SSE2, for `a * b + c`, `a * b - c`, and `c - a * b`: it adds to or takes from the register it gives its result in, so the addend is copied there first, and that register is neither of the factors'.
- **x86-64 builds vectors with the instructions of SSE2, which every x86-64 chip has,** and nothing of SSSE3, SSE4, or AVX. A vector is held in a register of floats or in the frame, where it takes 16 bytes, is passed and returned in the registers floats are, and is read and written by `movups`, which asks for no alignment, so no instruction but that one reads a vector from memory. `+`, `-`, and the bit operations of integers are `padd`, `psub`, `pand`, `por`, and `pxor` of the lane's size, and of floats `addps`, `subps`, and `mulps`, or the same for doubles. A product of lanes of 16 bits is `pmullw`, of 32 bits two `pmuludq`s and a shuffle that puts their halves together, of 8 bits `pmullw` of the even bytes and of the odd bytes put together, and of 64 bits is made by `imul` on each lane in the registers of integers, as SSE2 has no instruction for those. A comparison of integers is `pcmpeq` or `pcmpgt` of the lane's size, with the operands the other way round for `<`, followed by `pxor` with all ones for `!=`, `<=`, and `>=`; one of numbers read as unsigned flips the top bit of both first; and one of lanes of 64 bits is made of the comparisons of dwords, the low as unsigned numbers and the high as signed. A comparison of floats is `cmpps` or `cmppd` with the predicate for `==`, `!=`, `<`, or `<=`, `>` and `>=` being the others with the operands swapped, which holds for a float that is not a number exactly as the scalar comparison does. A choice by a mask is `pxor`, `pand`, `pxor`, which is `otherwise ^ ((then ^ otherwise) & mask)`, and by a number is that with the mask made from `neg` and `sbb`. One value spread is `movd` or `movq` and shuffles, a lane is read by `pextrw`, `movd`, or `movq` after a shuffle, and written by `pinsrw` 16 bits at a time. A sum of integers is shuffles and `padd`s, of bytes `psadbw`, and a sum of floats is `(l0 + l1) + (l2 + l3)` by `pshufd`, `addps`, `pshufd`, and `addss`. The first lane a mask has set is `movmskps` or `movmskpd`, `pmovmskb`, or `packsswb` and `pmovmskb` for words, then `or` with a bit after the last lane and `bsf`. Every instruction reads a vector in a register, so one in the frame is read into `xmm13`, `xmm14`, or `xmm15` first, and a result is worked out in them and put in its home last. A circle of copies that holds a vector holds one aside in `xmm15`. A fused product of lanes is the same instruction of 128 bits, `vfmadd231ps` and its relatives, or of doubles `pd`, worked out in a register that holds the addend and is not either factor's.
- **arm64 builds floats with the instructions of the base set, one for one.** `+`, `-`, `*`, and `/` are `fadd`, `fsub`, `fmul`, and `fdiv`, negation is `fneg`, a rounding to a whole number is `frintm`, `frintp`, `frintz`, or `frintn`, and a float of one size from the other is `fcvt`. A comparison is `fcmp` and `cset` on the condition that holds exactly when the comparison does: `eq`, `ne`, `mi` for `<`, `ls` for `<=`, `gt`, and `ge`, none of which holds for a float that is not a number but `ne`. A choice is `fcsel` on the number being not 0. A float from a whole number is `scvtf` or `ucvtf` of the number read as 64 bits. A whole number from a float is `fcvtzs` or `fcvtzu`, which saturate and give 0 for a float that is not a number, so the instruction of the form costs one instruction here, and 4 more, two compares and two `csel`s with their constants, for a size below 64 bits. A float constant is its bits made in `x16` and moved by `fmov`, and zero is `fmov` from the zero register. A fused product is `fmadd` for `a * b + c`, `fnmsub` for `a * b - c`, and `fmsub` for `c - a * b`.
- **arm64 builds vectors with NEON, which every arm64 chip has.** A vector is held in a register of floats or in the frame, where it takes 16 bytes, at a multiple of 16, and is passed and returned in the registers floats are, read and written as a `q` register. `+`, `-`, `*`, and the bit operations of integers are `add`, `sub`, `mul`, `and`, `orr`, and `eor` on the lanes' size, and of floats `fadd`, `fsub`, and `fmul`; a product of lanes of 64 bits, which NEON has no instruction for, is made by `mul` on each lane in the registers of integers. A comparison of integers is `cmeq`, `cmgt`, `cmge`, `cmhi`, or `cmhs`, with the operands the other way round for `<` and `<=`, and `mvn` for `!=`; one of floats is `fcmeq`, `fcmge`, or `fcmgt`, which are false for a number that is not one, with the operands the other way round for `<` and `<=` and `mvn` of `fcmeq` for `!=`, which is true for it. A choice by a mask is `bsl` on a copy of the mask, and by a number that with the mask made by `csetm` and `dup`. One value spread is `dup`, a lane is read by `umov` or, of a float, `dup` to a register of floats, and written by `ins`. A sum of integers is `addv`, or `addp` for lanes of 64 bits, and a sum of floats is `faddp` of the vector with itself and then of its first two lanes, which is `(l0 + l1) + (l2 + l3)`. The first lane a mask has set is `cmlt` with 0, which makes lanes whose top bit is 1 all ones, `shrn` to the 64 bits that are as many bits for each lane as there are, `rbit` and `clz`, which give the place of the first bit that is 1 or 64, and a shift right by the log of the bits of a lane, so that no lane set gives the number of lanes. A circle of copies that holds a vector holds one aside in `v31`. A fused product of lanes is `fmla` for `a * b + c` and `fmls` for `c - a * b`, which add to or take from the register they give the result in, so the addend is copied there first; for `a * b - c` the addend is made `fneg` first and `fmla` follows.
- **Inlining replaces a call of a small function with the function's instructions.** It is the first pass, a step of its own between the lowering and the targets, which neither knows of. A call is replaced when the function is called from one place only, or when the function's size is at most 4, or when the function calls nothing and its size is at most 40, and never when the function is cold. A cold function is one that is run rarely, which only the runtime marks, and its call stays however few places call it: its instructions and the values it needs stay out of a loop that calls it, so the registers of the loop hold the loop's own values. The function that grows a list is one. A function's size is the number of its instructions plus the number of its blocks, one for how each block ends. Functions are taken callees first, so a function is as small as it will be when a call of it is looked at, and only calls from the functions `main` reaches are counted. The caller's block is cut where the call was: what came before jumps to a copy of the callee's blocks, whose returns jump to a block that takes the call's results and holds what came after. A function that nothing calls is left out. A copy of a function that calls nothing adds no call for the later stages to work on, so such a function, once what it called is inlined into it, is replaced up to a larger size than one that calls: these are the small functions that read a byte or a flag, which the lexer in `compiler/lexer.smith` calls for every byte, and its instructions for a byte fall by almost a fifth. The same bound for every function costs the build of the lexer more for a few parts in a hundred fewer instructions, and weighing whether a call is inside a loop, or inside a function that is called from one, gained the lexer nothing more. The rule reads the scalar form and nothing measured from a run. The pass does one walk, repeats nothing until it stops changing, and gives the same program every time.
- **Trimming passes a function only what it reads, and takes back only what it makes.** It is the second pass, after inlining, because only a call that inlining left costs anything, and before folding, because a result it gives as the argument may be a constant that folding then works out. A parameter that no instruction that stays, jump to a parameter that is read, choice, or return reads is left out of the function and of every call of it, and so is a result that is the same one of the function's parameters on every return that is reached, which each reader of the call is given as the argument at that call. A parameter that is only handed on to a call that does not read it, or only given back, is not read. A value given back in another place than it came in, and a parameter given back twice, are results of this kind, each read as the argument of its own. The first block of a function that is jumped to by its own jumps has parameters that change in the loop, so its results are not taken away. Functions are taken callees first, so what a call leaves out is known when the function that makes it is looked at. `main`, which the system starts with the parameters `ARGUMENTS` lists, keeps them. The form has no function whose address is taken. A function in a ring of calls, which the form has none of yet, keeps its parameters and results, and the calls it makes of other functions are made as they now are. The pass does one walk, repeats nothing until it stops changing, and gives the same program every time. A struct handed through a call so costs what its changed fields cost: a function that changes three fields of a struct of twenty and reads five takes the five and gives the three.
- **A function whose last act is a call of itself is a loop.** It is the first pass, before inlining, and is timed with it as the stage `inline`. A call of the function from itself is a tail call in the scalar form when its block returns the call's results as they are, or jumps with them, in order, to a block that holds no instruction and returns what it was given, as the block that ends an `if` or a `match` does, and nothing else reads them. Such a call is a jump to the start of the function with the call's arguments, so the function holds no call of itself and an executable of it runs in the one frame however many times it goes round. The first block of a function holds its parameters and nothing jumps to it, so the pass puts a new first block before it, which takes the parameters and jumps to the old first block, which is the head of the loop; every other block is numbered one higher. A call that anything is done after, a call of another function, and a function with no call of itself are left as they are, and so is `main`. What the checker accepts as a tail call, and the `decreases` that proves the loop ends, are [Recursion](language/recursion.md) and [Termination](language/termination.md), and the pass does not look at them.
- **A function that calls itself is checked for its `decreases` and for where the call is.** A call of a function from itself is a tail call when it is the last expression of the body, the last expression of a block of an `if` or a `match` that is itself in that place, or what a `return` gives: a call under `try` or `with`, as a part of an expression, or as the value of a binding is not. A function that calls itself needs a `decreases`, unless it calls itself only on a part of its argument, as the end of this item says: one or more parts separated by commas after the signature, each a whole number of an unsigned type over the parameters that is checked as a contract is, with no proof that it does not overflow, and is never lowered, so it changes no executable. At each call of itself, a tail call or not, `arith` proves, from what is known where the call is made and the arguments in place of the parameters (a default for a parameter the call leaves out), that no part of the measure is below zero and that the measure is smaller than it is now, as words are in a dictionary; a goal it cannot prove is an error at the call that says which, as the error of a `loop decreases` does. The call is lowered as an ordinary call, and a tail call is made a loop, so a function that calls itself last needs no frame for each call. A call that is not a tail call keeps a frame, as the next bullet says, in the memory of `alloc`, so the function must carry `alloc`, and a function that does not is refused as any missing effect is. A circle of functions, which the checker finds as the calls are walked, needs each function to have a `decreases` of the same number of parts, an error naming the circle otherwise; each call from one function of it to another is held to the measure the callee states, the goal that cannot be proven being kept when the call is checked and given when the walk finds that the callee calls back; and when a call of the circle is not the last thing a function does, each function of it carries `alloc`, as the frames of a function that calls itself are kept. A call of itself in a lambda is refused as not supported yet. Each call of a function notes the places at which it passes a part of the caller's parameter at the same place: a name that a `match` on the parameter, or on a part of it, binds in any pattern but a bare name, a field of it or of a part, the name of a `loop` over a `List` or a `Slice` that is it or a part, or a piece of it or of a part that `arith` proves has fewer elements; a name that can be assigned is never a part. A function, or a circle of functions, that has no `decreases` is accepted when the functions that call one another with it by the calls noted pass, at every such call, a part at one place that all of the calls share, as a value holds only so many parts; anything else is refused with the error that names the missing `decreases`. A copy of a function that calls itself is not walked again for the call, as it is a loop or a stack of its own.
- **A function that calls itself, where the call is not the last thing it does, has a stack of its own.** The lowering makes the calls of a function from itself that are the last thing it does jumps, as the first pass does, and then gives each function with a call of itself that is left a stack in memory, before the stacks of `alloc` are passed. The function is cut at each such call. A call is a push of the values that are alive when the call returns and of a number that says where it went on, and a jump to the start of the function; a return is a pop, which reads the number on the top and goes on in the piece it names, with the values back as parameters. The stack is a run of chunks of at least 64 KB, each asked of the system as any memory is, the first when the function is entered, with a frame at its bottom that makes the function return when it is popped, and the next when the chunk has not room for the frame, with a frame at its bottom that says where the chunk before ended. Where the free memory in a chunk begins, and how many bytes of it are left, go from block to block as a stack of `alloc` does, so the requests for chunks are found by the handler as any request is and are released with the function's temporaries when it returns, and no depth of calls overflows the system's stack: it is bounded by memory. The pass is `scalar::recur`, which the lowering runs; a function that cannot reach itself is not changed. Functions that call each other are first made one function: a circle of functions, each of which reaches each of the others by calls, becomes one function that takes a number saying which of them it is, the parameters of all of them, and returns the results of all of them, of which a caller reads those of the function it called. A call between two functions of the circle is a call of the one function, with the number of the callee and made-up values for the parameters the callee does not read, so `tail` makes a loop of one that is the last thing a function does, and each function of the circle is left as a function that calls the one function, so no call from outside the circle changes. The pop is one block that every return reaches, and a piece after a call that is in a loop of the function as it was written is not entered from it: a jump into the middle of a loop is a way in that does not pass the loop's header, and the blocks of such a function cannot be written as `loop`, `block`, `if`, and `br`. So in a function that has a loop, every pop goes on to the function's start, and from there through the header of each loop the piece is in, outermost first, to the piece. The start and each such header are blocks that take, besides what they took, the number of the call that is going on in the loop, or 0 for none, and what the piece after each call through them takes, and every other jump into them gives 0 and values that nothing reads. A function with no loop has no such blocks, and its pop goes to each piece as before.
- **Threading sends a jump past a block that only chooses.** It is the third pass, after trimming, because a call that is left is a call that threading cannot go through, and before folding, which then works out what the jumps it made give. A case that is built and matched at once, as `match byte_at(src, i) { .some(b) { f(b) } .none { g() } }` is once `byte_at` is inlined, is built by jumps that give a block the number of the case, and matched by that block choosing on the number. A jump into a block goes where the block would send it when the block writes no memory and calls nothing, and what the block chooses on is known from what the jump gives: a constant, or a value that the block's instructions work out from constants. The jump gives the block it goes to what the block would have given, and the walk goes on from there, so a chain of such blocks is gone through, but never through more blocks than the function has. A jump whose block chooses on a comparison, or on a choice between two constants made on one, from the one jump that ends its block, ends instead with the choice on the comparison, with the answers of the two cases. A value that a block makes and another block reads is given on to the block that reads it as a parameter when that block is only jumped to from it, one block after the other, and a constant that the block makes is made again where it is read, so a case's number is made only when something still reads it where the jump does not go. A block that makes a value that is read where the jump goes in another way is not gone through. The number of the case is neither made nor read when nothing reads it after the choice, which `remove` finds when it takes away the blocks nothing reaches. The pass does one walk over the blocks of each function, from the last to the first, so that a jump that goes into a block that was already sent on goes where that block goes in one step, and a chain of blocks is not gone through again from each of its blocks. The constants a jump gives are made once, for the jump the walk ends on, and not for each block it went through. Each jump is gone through at most as many blocks as there are in the function. A function whose blocks are written as loops and branches stays one: when the jumps it sends on make a function that was one into one that is not, the pass is run again on the function as it was, leaving alone every block that a jump back goes to and that dominates the jump, which is the header of a loop, so that no jump is sent past the header into the loop.
- **Folding replaces an instruction whose inputs are all known by its answer.** It is the fourth pass. A value is known when it is a constant, or a parameter that every jump into its block gives the same constant, or a choice made on a known value. An instruction that reads no memory and calls nothing, whose inputs are known, becomes a constant. A choice between two values on a known value is the value it chooses, and a block that ends by choosing between blocks on a known value ends with a jump. A block that ends by choosing between two blocks on a comparison's value with its bit flipped by an `xor` with 1 chooses on the comparison, with the two blocks the other way round. An addition, subtraction, `or`, `xor`, or shift whose second value is the constant 0, and a multiplication by the constant 1, is its first value, which holds for an address moved by 0 bytes too. The answer is worked out by the code the evaluator uses, so the two cannot disagree. The pass does one walk over each function, each block after the blocks that jump to it except by a jump back, and a parameter of a block that is jumped to by a jump back is not known. An address is moved by a number of bytes at run time, and the form has no constant for one moved, so that is left.
- **Working out the same thing once replaces a second by the first.** It is the fifth pass. An instruction that reads no memory, writes none, and calls nothing is the same as an earlier one when it does the same to the same values and gives the same type, and a constant counts, so a constant is made once in the blocks its first making reaches. The second is taken away and its value is the first's when the first is in a block that every path to the second's block passes through, or earlier in the same block. The pass does one walk over each function's tree of dominators, and an instruction whose inputs were replaced is found in the same walk. A read through an address is never replaced, as the form does not say what a write may change. Two instructions that do the same to the same values in the other order, such as `a + b` and `b + a`, are not the same.
- **Removal takes away what nothing uses.** It is the sixth pass. In one walk for each step, it takes away the blocks that nothing reaches, then reads a parameter that every jump into its block gives the same value as that value, then takes away each instruction whose values nothing uses, unless it writes memory, calls a function, or calls into the system, and each parameter that nothing uses, with what every jump gave it, and last joins a block that is jumped to once, by a block that ends with a jump, to that block. Before all of these a jump to a block that holds only a jump goes where that block goes, giving what it would have given, which leaves no block that holds only a jump, except a function's first block when the block it jumps to is a loop's, jumped to from elsewhere, and a block that more than one jump gives a value that a block after it reads, as there is nowhere else for the values to become one; a choice between two jumps that are the same is that jump; and a block of at most one instruction that jumps on, and is jumped to by plain jumps only, is copied into each block that jumps to it when the function is no larger for it, so that a loop's counter is added in the block that ends the round and not in a block of its own that hands every value on again. The first two of these take each block after the blocks it jumps to, so a choice that is a jump once its comparison goes, and the block it leaves with only a jump, are skipped by the blocks before them in the same walk, and a chain of them is one walk and not a walk for each. What a walk can leave for another is a parameter that skipping gave the same value from every jump, and a copy of a small block, which one more walk takes, so removal makes at most four walks, and makes another only when the steps that skip, join, and copy changed the function in the one before. That is a number that does not grow with the function: a function of ten thousand blocks takes as many as one of ten, which a test counts, and no program the generators build needs more than three. A function that needed more would be left with the work and be no less right. Removal then makes a choice on the value that the end of its block chooses on, a `bool` that a comparison gives, in the blocks that only the jump for each answer leads to, where the value is known, and takes the choice away when nothing else reads it: the blocks are those the target of the jump dominates, when no jump from outside them leads to its first block but this one, and a jump from inside them back to it keeps the answer, so a choice that a loop reads is made too. Last it moves a comparison that only the choice ending its block reads to the end of the block, where a target finds it. A value is used when a return, a choice between blocks, an instruction that stays, or a jump that gives it to a parameter that is used reads it, so a value a loop only gives on to itself is not used. A loop's parameters that stand for one another, such as two that start as the same value and swap, are left. The values that are left are then numbered from 0 with no gap, in the order they are defined, block by block, a block's parameters and then what each of its instructions makes, so that a value that a pass took away leaves no number behind.
- **The passes are a fixed list,** each roughly linear in time, run in this order: making a loop of a function whose last act is a call of itself, inlining small functions, trimming what a function is passed and gives back, sending a jump past a block that only chooses, folding constants, working out the same thing once, and removing what nothing uses. Nothing iterates to a fixpoint: removal makes at most four walks over a function, as it says, and value semantics means no alias analysis is needed. Each pass takes the form to the form, so a pass is tested by running a program before it and after it. A pass costs what it changes, not the program it is given: it takes the program, changes the lists of a function where they are, and allocates a table or a buffer for a function or for the pass, in proportion to the values and blocks of the function, and nothing for a block or an instruction it leaves as it is. A pass never runs an instruction that may break what it is given, a division, on a path the source did not take. Every pass does so, and inlining moves the blocks of a function that has one call into the caller. Each pass takes time in proportion to the blocks, instructions, and values of the function it is given, and leaves a function no larger than that, and a test builds a program at two depths, one twice the other, and fails when a pass leaves, allocates, or goes through more of the blocks of threading than in proportion to what it was given.
- **A target is thin.** For each kind of chip, instruction selection picks instructions for the form's operations, and tuning for that chip happens there. One register allocator serves every chip and is told its registers: values live in registers, and only what does not fit goes to the frame. A frame holds a place only for a value that remains: the numbers of the values a function is left with have no gap, so no place is held for one that a pass took away. Calls between Smith functions pass arguments and results in registers, by one convention for each kind of chip on every system, and only a call into the system follows the system's convention.
- **What a pass reads of an instruction and of a block's end is given where it is held, and costs no memory.** The values an instruction reads, the values a block's end reads, its jumps, and the blocks it may go to are given as an iterator or a slice of the form itself, so that a walk that looks at each of them asks for none; a pass that needs them kept makes one list for the pass and not one for each instruction.
- **A branch on a comparison is one compare and one branch.** A choice between two blocks that is made on a comparison that nothing else reads, which removal leaves as the last instruction of its block, is not made a value in a register and tested: a target compares the two values and branches on what it found, with the immediate form of the compare when the second is a constant that fits, and the compare reads a value of 8 bytes that is in the frame where it is. A jump that gives its block nothing to move is the branch itself, so a choice is one branch and the code of the other jump, and when both give nothing to move, the one that follows is the block that comes next. A conditional branch of arm64 reaches 1 MB, so a branch back to a place more than that behind it, such as the code that ends the program when the system refuses memory, goes over an unconditional one, and so does a branch to a block in a function in which one does not reach, which is written again. A constant is made in each block that reads it, before the target gives values their homes, and on the way to a block it only a choice gives it to, so it is not kept in a register or in the frame across blocks; an instruction that reads a constant as its second value holds it in itself when it fits: 32 bits on x86-64, and 12 bits for an addition or a subtraction on arm64. A choice between two values that is made on a comparison that nothing else reads, and that is the instruction before it, is the same: a target compares and moves on what it found, and when the first value is a constant it is put in the result and the second is moved when the comparison does not hold, so a constant costs one instruction and the choice one more. A number of more than 16 bits whose half-words are mostly all ones is made by a `movn` on arm64, so the greatest number of a type is one instruction there. An addition of 8 bytes is one `lea` when its result is not in the register of an operand. With these a push that has room, in a loop that pushes to a `mut` list, is the compare and the branch of the loop, the compare and the branch for the room, a store, two additions, and the jump back, which is 8 instructions on x86-64, and a test counts them from the bytes. It is 9 on arm64, which makes the loop's bound in the round, as a constant is made in each block that reads it, and 10 or more when the bound does not fit 16 bits. Rust built with `-O` takes 7 for the same loop, so a round is at most twice its instructions.
- **A write at a base and an index times the size of what is written is one store.** A store whose address is the sum of a base and an index of 64 bits times 2, 4, or 8 is written as one instruction that reaches `base + index * scale`: `mov [base + index*8], r` on x86-64, and `str xt, [xn, xm, lsl #3]` on arm64, where the scale is the number of bytes written. It is taken when the multiplication and the addition are the two instructions before the store, apart from constants that the target holds, and nothing else reads what either makes, so that the base and the index are in the places they were in when the store is made. The multiplication and the addition are then not made, and neither is the constant that the multiplication reads on arm64. A read at such an address is not taken, so a program that writes no element of a list is as it was.
- **Comparing two whole numbers, or two `bool`s, is one comparison.** `<`, `<=`, `>`, `>=`, `==`, and `!=` of values of a whole number type or `bool` are lowered where the program is lowered to this form, and not through the `Ord` and `Eq` of the prelude, which no program can write for these types, so the answer is never built as an `Order` and read back: `==` is one equal, `<` and `>` are one less-than with the operands the right way round, as signed or unsigned numbers by the type, and `<=`, `>=`, and `!=` are the opposite comparison with its bit flipped by an `xor` with 1. A call of `compare` or `eq` through a function with a type parameter bound by `Ord` or `Eq` is the same once the function is made for the whole number type. Folding makes a choice on a comparison with its bit flipped a choice on the comparison with its blocks the other way round, so `if a <= b` is one compare and one branch, as the item before this one says. A type of a program's own, and a struct, enum, tuple, or text, is compared by its `Ord` and `Eq` as before.
- **`/` and `%` are one `Binary` instruction each, and an unsigned power of two is a shift or a mask.** `/` of two whole numbers is `DivU` or `DivS` and `%` is `RemU` or `RemS`, by the sign of the type the operands are taken to. The operands are taken to the hull of both and of the result's exact range, so that the instruction sees numbers of one size, and a signed `%` whose first number may be the least of a size below 64 bits and whose second may be -1 is taken to twice that size, as the processor's instruction would fault on the quotient it does not give. The result is taken to the size of its exact range. An unsigned `/` by a literal power of two is `ShiftRightU` and `%` is `And` with one less, so no instruction divides. The checker asks the prover for `divisor != 0` and, at a signed 64-bit size, for the quotient to fit; so no instruction tests either, as the next bullets say.
- **A `wrapping_` or `saturating_` addition, subtraction, or product is lowered at the call, and costs the operation and the choice.** A call of one of the six functions, of `std.int` or of the trait `Wrapping`, for every whole number type is lowered where the program is lowered to this form, as `==` is, so no call, frame, or return is left, and the function that only calls the one the compiler builds is no function of the program. `narrow` and `clamp` are lowered at their call too, and `wrapping_div` and `wrapping_rem`, of the trait and of `std.int`, are lowered at their call too, as one division of numbers that cannot fault: the divisor is chosen as 1 where it is -1, and the choice gives the dividend negated, or 0 for what is left over. `wrapping_` is the `Binary` instruction. For the others the instruction that says whether the answer fitted, as [Scalar form](#scalar-form) says, gives the answer and that, and the rest is one choice. `saturating_` chooses the end on that: the greatest number of an unsigned type for a sum or a product, 0 for a difference, and for a signed type the end that the signs say, which is the least or the greatest number by the sign of an operand and is worked out before the operation, so that nothing that changes the flags comes between the operation and the choice. An addition or a subtraction of an unsigned number of fewer than 64 bits is shorter as a comparison, since the numbers do not have to be widened to see whether they fit: the sum wraps and did not fit exactly when it is below an operand, and the difference when the first operand is below the second, so `saturating_add` is the sum, a comparison, and a choice, and `saturating_sub` is the greater of the two operands less the second. `clamp` of a float is the float rounded to the nearest whole number, as `round` is, compared with the least float that is not below the range and with the greatest that is not above it, and cut to an integer, which is exact between the two, with a choice of each end: a float that is not a number is not at most the greatest, so it gives the greatest with no comparison of its own. `narrow` of a float compares the float itself with the same two floats and with itself cut toward zero, as `trunc` is.
- **A choice by a number costs the same however many blocks it chooses between.** A block ends by going to the jump at the place `on`, an integer that is below the number of jumps. A choice between 5 or more jumps is made through a table, and not by comparing `on` with each place in turn: after the code of the program there is a table for it, with 4 bytes for each jump, which are how far the code of that jump is from the start of the table. The choice loads the entry at the place `on`, adds the start of the table to it, and goes there, in 4 instructions on x86-64 (`lea`, `movsxd`, `add`, `jmp`) and 5 on arm64 (`adrp`, `add`, `ldrsw`, `add`, `br`), whatever the number of jumps. The code of a jump is the block itself when the jump moves nothing, and otherwise the moves and then a jump to the block, which follow the choice. A choice between fewer jumps compares `on` with each place but the last. A `match` on whole numbers is lowered so that `on` is the distance of the value from the least literal when the literals lie close together, which is when the distance from the least to the greatest is at most 4 for each literal, and so the choice is made through a table. A `match` of 3 literals or fewer, and the sets of literals that remain when one is split, are chosen by comparing the value with each in turn.
- **Registers are offered by kind.** A chip tells the allocator its registers of each of two kinds, the registers of integers and addresses and the registers of floats and vectors, and for each kind in two lists: those a call may change, and those it does not. It keeps for itself only what instruction selection cannot do without. The allocator gives each value one home for its whole life, a register of its kind or a place in the frame, and a float is never in a register of integers nor an integer in one of floats. A vector is held in a register of floats, and is never in a register across a call: a register that a call leaves alone may leave only part of a vector, as `v8` to `v15` of arm64 do, so a vector alive across a call is in the frame on every chip. A register has one number on the chip, the registers of integers first and the registers of floats after them. Everything below holds for each kind alone: no more values of a kind are held in registers than the chip offers of it, and no more are held across a call than it leaves alone. A value that is alive across a call takes a register the call does not change, or a place in the frame. Any other value takes a register a call may change first. A function with no value alive across a call is offered only the registers a call may change, so it saves and restores nothing however many values are alive together, and what does not fit goes to the frame, unless it calls nothing and has a loop: it is then offered every register. A register it must save costs a save and a restore each time the function runs, however long the function is, so where each value is used about once a place in the frame is no dearer; but a value in the frame costs a store and a load in every round of a loop, which the save and the restore, paid once, do not. A function has a loop when a walk from its first block comes to a jump to a block it is still inside. A function saves a register a call does not change, in its prologue, only when it uses one. A call into the system counts as a call, and it may change every register a call may change, taking the widest of the three systems of the chip, so the three targets of a chip share their code. This is Smith's own convention, one for each kind of chip on every system.
  - **x86-64** passes the first five arguments that are not floats or vectors, and the first five results that are not, in `rdi`, `rsi`, `r8`, `r9`, and `r10`, in that order. It keeps `rax`, `rcx`, and `rdx`, which multiplying and comparing need, `r11`, which holds the value that breaks a circle of copies, and `rsp`. A call may change `rdi`, `rsi`, `r8`, `r9`, and `r10`. A call does not change `rbx`, `rbp`, `r12`, `r13`, `r14`, and `r15`. It passes the first eight floats or vectors, and gives the first eight results that are, in `xmm0` to `xmm7`, in that order, and holds floats and vectors in `xmm0` to `xmm12`. It keeps `xmm13`, `xmm14`, and `xmm15`, where instruction selection works out a result and holds a float or a vector read from the frame. A call may change all of them, as a call into the system of any of the three systems does, so no float is alive across a call in a register: it is in the frame, and a function with floats alive across no call saves nothing.
  - **arm64** passes the first fifteen arguments that are not floats or vectors, and the first fifteen results that are not, in `x0` to `x14`, in that order. It keeps `x15`, which reaches a place in the frame that is far from the stack pointer and holds the entry of a table, `x16` and `x17`, which instruction selection works in, with `x17` also holding the value that breaks a circle of copies and the address of a table, `x18`, which a system may own, `x29`, `x30`, and the stack pointer. A call may change `x0` to `x14`. A call does not change `x19` to `x28`. It passes the first eight floats or vectors, and gives the first eight results that are, in `v0` to `v7`, in that order, and holds floats and vectors in `v0` to `v7` and `v16` to `v28`, which a call may change, and in `v8` to `v15`, of which a call keeps the low 64 bits, which hold any float, on every system, so a float alive across a call is in one of those eight when it can be, and a function saves each it uses in its prologue as it saves `x19` to `x28`. It keeps `v29`, `v30`, and `v31`, where a float or a vector read from the frame waits and a result that goes to the frame is worked out.
- **A call passes values in registers.** For each kind of chip one convention, the same on every system, names which registers of each kind carry a call's arguments, in order, and which carry its results. They are among the registers a call may change, so no value alive across a call is in one. The k-th argument of a kind is in the k-th of the registers of that kind, and the k-th result of a kind is in the k-th of them, and an argument or result of a kind after the last register that carries one of it goes through the frame, at its size. A function with more floats than registers builds. The allocator is told how many registers of each kind carry them, and gives a parameter that arrives in a register that register when no value alive holds it and the parameter is not alive across a call, so a function that uses its parameters where they arrive copies nothing. A call moves its arguments to their places, and takes its results from theirs, as a jump gives its values, as if all were copied at once.
- **A value is moved only when it must be moved.** The allocator names the register each value would like and gives it when no value alive holds it and the value may have it. A parameter of a block would like the register of a value a jump gives it, the register most of them are in first, so a jump moves nothing for it, and two parameters that a jump swaps are given each other's registers when no other value needs them. A result would like the register of the parameter it is given to, so the addition that ends a loop's round is made in the register of the counter. A value would like the register a call passes it in, takes it from, or a function gives it back in. A loop whose parameters are handed round as they are moves nothing. A constant that every read holds is given no register and no place in the frame, and is not made: a store of a constant on x86-64 writes it in the instruction, a jump, a call, and a return give it by moving the number to where it goes, and a choice makes it where it is read. A constant that any other read needs, such as an address, is made in a register as any other value. A value read from the frame into a register that instruction selection works in is not read again in the block while that register has not been changed, and nor is a result it wrote there, which on x86-64 are `rax`, `rcx`, and `rdx`.
- **A `return` is a jump, or the end of a function.** In a function, the block a `return` is in ends by returning its values, and what is written after it is a block nothing reaches. In a lambda, which is lowered in the place it is called, and in a function lowered in place, the block jumps to the one where the values it gives meet those the body ends with, and a `return` adds no call and no copy. A function whose last line is `return e` has the instructions of the one that ends in `e`.
- **The form runs.** It has an evaluator, which says what a program in it does, and that is what each target's executables are tested against. It has no network and no clock of its own, and answers `Kind` as Linux, as a WebAssembly module does, so that a server that is given a handler of `net` runs in it.

The idea of keeping several levels, and lowering through them one step at a time, is the one MLIR is built on. Smith borrows the idea and none of the code. Each level here is its own small type with its own evaluator, so every step from one level to the next has the same test: a generated program does the same thing before the step and after it.

**An operation of a `Secret` takes a time that does not depend on its operands.** [`Secret`](library/secret.md) is a struct of the library, and the form marks the operations made of one. Each target lowers a marked operation to instructions whose time is the same for every operand, and no pass makes one a branch or an address. This is planned, as `Secret` is.

## Effects

Effects are checked and then erased, so a permission costs nothing at run time.

- **A handler is resolved at build time.** The handler in force at each call is known from the source, so a function is compiled once for each handler it runs under and its operations become direct calls. Under the operating system's handlers they are system calls.
- **Copies are the product of the handlers a function runs under.** A function is built once for each choice of the handlers it runs under, with a handler being the function that handles the effect and not each `with` that installs it, so a function under two handlers that each run under two others is built four times. What a handler holds is passed to the copy.
- **A handler's state is passed, and never global.** A handler that holds state, as an arena holds where its free memory begins and how many bytes of it are left, keeps it in values that start where the handler is installed. Every function compiled to run under that handler takes the values of the state as its first parameters, which the source does not show, passes them on to each function it calls that carries the effect, and gives them back as its first results, and each of its blocks takes them from the jump that enters it. So the scalar form needs no memory that every function can write, a program has no state that two tasks share by accident, and installing a handler inside another is new values with nothing to save or put back. The scalar form has no place in a frame that holds an address, and the values need none: a request that finds the piece that has room is arithmetic on them. Inlining and the passes treat the parameters as any other. The handler of `alloc` that start-up code installs is one of these. Its state is two stacks of memory, each as where its free memory begins and how many bytes of it are left, one for the results of functions and one for their temporaries, as [Memory a function gives back](#memory-a-function-gives-back) says, and start-up code gives `main` two that have no bytes, so that the system is first asked when the program first needs room.
- **Start-up code installs the real handlers.** The entry point of an executable is Smith code from the standard library. It installs the operating system's handlers for the effects `main` lists and calls `main`. No part of the compiler or the library reaches the system by any route a program could not use.
- **Suspension is a property of the copy.** The copy of a function that runs under the scheduler in force is a state machine, and the copy under a blocking handler is ordinary code.
- **A wait is an instruction of the scalar form, and a function that has one is cut into states.** `System::Suspend` takes two 64-bit integers, the kind of the wait and its handle, and gives nothing. A function suspends when it runs one or calls a function that suspends, and the pass `suspend` makes each such function two functions. The start is at the place the function was and takes the address of the function's frame and then its parameters, saves them in the frame, and gives nothing. The poll takes the address of the frame and runs the task to its next wait or its end, and gives a status of 8 bits, which is 0 when the task is done and 1 when it waits, and the kind and the handle of the wait. What the function gave is written in the frame, at a place of its own for each value, when the task is done. A function the pass adds, `poll any`, takes the address of any frame, reads from the frame's header which poll runs it, and polls it, so that a scheduler holds frames of many functions and knows none of them. Polling a frame again resumes the task, and a program that does not suspend is given back as it was. The evaluator answers a wait from what the test says is ready and notes it, so that a wait that is over at once and a task that is suspended and resumed run the same code after it.
- **A frame has a layout of its own for each function, and holds the frames of its callees.** It has, in order, a header of two words, the number of the state and the number of the poll that runs the frame, the places for the values the function gives, the parameters, one place for each value that is alive across a wait, and the bytes of each `Frame` instruction and the frame of each call of a function that suspends, each of those a multiple of 16 from the start. A value that is alive across a wait is written where it is made and read where it is used, so a path that resumes needs nothing made again, and a block parameter is written as the block is entered. The poll starts by going to the state the frame says. A wait saves the number of its state and gives the wait. A call of a function that suspends starts the callee in its place in the frame, saves the number of its state, polls the callee, goes on with what the callee gave, which it reads from the callee's frame, when it is done, and gives the callee's wait when it is not, so that the next poll goes to the callee again, down the chain of frames. The frame of the task is asked of the task's arena once, with the bytes the pass says, and no more memory is asked while the task runs. The lowering runs `recur`, then `suspend`, and then the passes that install the handler of `alloc`, so a function that calls itself and waits has a stack of its own in memory, as any function that calls itself has, and the pointers into that stack are values saved in the frame across a wait: the frame holds a fixed number of bytes however deep the recursion goes, and every function the pass is given is one that no call reaches itself. `main` cannot suspend.
- **A lambda given to `__frame` is a function of its own, with what it reads passed in.** A child task's work runs after the call that made it has moved on, so it is not lowered in place, as every other lambda is. The lowering finds each name of the function around it that the lambda reads, and each name that the functions of the handlers in force where `__frame` is written use, by looking at the bodies, and the lambda becomes a function that takes the scalars of those names as parameters, in the order the frames and names are found. A name that holds a function is not a parameter: the function it holds is lowered into the new function, with the names it reads found in turn. The frame of that function holds the parameters, as it holds those of any function that suspends, so what the lambda reads is saved in the frame when it is made. A name the lambda takes is moved into the frame, and the checker spends it at `__frame`. A name it reads and does not take is copied as its scalars, and a `Frame` can only be made where `std/` makes it, so nothing outlives a name it was lent. A lambda that reads an array kept in the frame of the function around it, and a lambda under a handler whose functions assign a name, are refused with an error that says they are not built yet, and are never accepted with the state copied.
- **A frame is made by a function the pass `suspend` writes.** The lowering places, for each lambda made a frame, the function it becomes and a function that makes its frame, which takes the same parameters and is empty until `suspend` runs. `suspend` takes each function the lowering made a frame of as a task, whether it waits or not, and writes the starter: it asks the arena in force for exactly the bytes that task's frame has, starts the task in them, which writes the header, and gives the address of the frame and its number of bytes, which is what a `Frame` holds. The place of `poll any` is placed by the lowering too, so `__poll` is a call of it. What a task gave is at places that depend on the types alone, from byte 16, so `__result` reads a frame of any function that gives the type without knowing which function it is of, and the checker accepts it only for the type the lambda of that frame gives, which it knows from the call of `__frame` the frame was made by, directly or through the one name that call defined, and refuses a frame read at another.
- **`Frame`, `__frame`, `__poll`, `__result`, `__wait`, and `__drop` are the library's.** `Frame` is a struct of `std.task` without `Copy` and `Discard`, so it is used exactly once, by `__result`. `__frame(work: take fn() -> T) -> Frame` makes a lambda a frame. `__poll(frame: Frame) -> Poll` runs the frame to its next wait or its end, and gives `.done` or `.waiting(w)`, where `w` is the `Wait` the task suspended with. `__result(frame: take Frame) -> T`, where `T` is the type of the place its value goes to, gives what the lambda gave. `__wait(w: Wait)` is `System::Suspend` with the number of the wait's case as its kind and the handle it holds, and gives nothing until the task is polled again. A `Wait` is `.read(h)` or `.write(h)` of a handle, `.time(ms)`, `.task(t)`, or `.read_by(h)` or `.write_by(h)`, each holding a number of 64 bits, so a wait is still a kind and one word; the milliseconds of the last two are given to the scheduler by the operation `limit` just before the wait, so that the handle and the milliseconds are each whole. A program that calls one outside `std/` is refused, as it is for `__system`.
- **A child task is a frame that a scheduler holds, and a group is the scheduler of its children where none is in force.** `task` is an effect that `std.task` declares, with `start(work: take Frame) -> u64` and `finish(child: u64) -> Frame`, and `spawn[T]` and `join[T]` are generic functions of the library that carry it and call them, so no handler of `task` is generic. `spawn` is `Task(number: start(__frame(work)), ...)`, and a `Task[T]` holds the number `start` gave and no frame, since a `Frame` is used exactly once and a scheduler that keeps the frame of a child in its queue cannot also hand it to the `Task`. `join` is `__result(finish(child.number))`. `with tasks()` is a handler of `task`, and which of two it is is known when its copy is built, as `__scheduled()` is: where no scheduler is in force it is the scheduler of its children, written in Smith in `std/task.smith`, and where one is in force it hands each `spawn` to that scheduler through `start`, with the frame at the number it made, and `join` waits there, so a group inside a task never opens a second loop, which would hold up every other task while it blocked. `main` is a plain function and `tasks()` carries no `task`. `__address(frame) -> u64` gives the number of a frame and lends the frame, and `__frame_at(number: u64) -> Frame` makes the frame at a number; both are the library's, as `__frame` is, and the form has no instruction between an address and a whole number, so each goes through a place of the function. A child is given as a lambda that `__frame` makes a function of its own, so what it gives away moves into it, and the checker refuses a child that assigns a `mut` of the function it is written in.
- **The group that is the scheduler waits in `epoll` on Linux and in `kqueue` on macOS, on one thread.** Its state is the lists of the tasks it started and ended, of those that wait for another task, and of those that wait for a descriptor, with the descriptor of `epoll` or of `kqueue`, made when the first task waits for the system or for a time and closed once where the group's block ends, so that a group that made none closes nothing, and a turn counter. It runs a task until it waits, and a task that waits for a descriptor is registered once, as the kernel's one-shot event for it, and parked until `epoll_wait` says the descriptor is ready, which it asks only when no task can run, so a program holds one thread however many connections it serves. The kernel's calls are three more `Raw` calls of `__system`, `EpollCreate1`, `EpollCtl`, and `EpollWait`, with the numbers of Linux on x86-64 and arm64, and on macOS they give minus 38, as no group waits there with them. macOS waits with two more, `Kqueue` and `Kevent`, which are the wrappers of `libSystem` of those names and which give minus 38 on Linux, so that one copy of the scheduler is built for every machine and asks the kernel its `Kind` to choose. A task is registered with one `kevent` of 32 bytes, the descriptor, the filter that reads or writes, and the flags that add it and drop it once it has said so, which is the one-shot event of `epoll`, and the scheduler waits in a `kevent` that gives one event, whose first bytes are the descriptor, with no time when no task can run and a time of nothing when some can. A call that would block gives minus 11 on Linux and minus 35 on macOS, and the flag that makes it not wait is 64 and 128, which `std/net.smith` writes for the kernel it is built for. A program that waits imports `kqueue` and `kevent`, with the other wrappers, and nothing else of the library. An event is read from the buffer by the three bytes that are the same on both layouts of the kernel's event, as the descriptor is written there three times. A task waits for a time by a wait that holds the milliseconds from when it waits, and the scheduler turns them into a moment of the clock it keeps: the group reads the monotonic clock with one more `Raw` call, `Now`, which is `clock_gettime` as `ClockGetTime` is and is built into the scheduler for every machine, where it gives minus 38 and is never run on a machine with no clock, and only while a task waits for a time; the group closes its queue with one more, `CloseQueue`, which is `close` as `Close` is for a socket and is built into the scheduler for every machine, so that a group asks nothing of a machine that has no network, where it gives minus 38 and is never run; the scheduler of a test keeps a time of its own, which starts at 0 and goes forward to the nearest moment when no task can run, so a test of a timeout takes no time. The moment is in the fourth word of the frame's header, with the state bit 16 that says the task waits for a time and the bit 32 that says its time and not its handle woke it, which `timed_out` reads; a task that waits for a handle until a time has both bits, and is woken by whichever comes first, and the group asks the system's queue what is ready with the nearest time as its timeout, in `epoll_pwait` in milliseconds and in `kevent` as a pair of the seconds and the nanoseconds. The tasks that wait for a time are found by the chain of the tasks, which every other queue is, so no memory is asked for them. A task waits for a descriptor by an operation that tries the call that does not wait, `MSG_DONTWAIT`, and waits only when the kernel says it would block. `__scheduled()` is the library's, true in a copy built for a scheduler that holds state and false in the others, so the operations of `net`, which carry `task`, suspend in a group and block as they did everywhere else, and a program with no group is built as it was. A test of I/O is `test_scheduler_with_io`, whose handles are made ready by the test in an order it gives.
- **What a task holds across a wait lives until the task ends.** The passes that install the handler of `alloc` give a function's temporaries back when the function returns, and a poll returns at each wait, so a poll gives its temporaries back only when its task is over: everything a poll builds goes on the stack of results, the pair of a call of a poll is kept, and a `with arena()` around a wait opens and closes nothing inside a task, which releases no memory until the task ends. A loop carries the state of the scheduler, as it carries what its body assigns, since a wait or a `spawn` in the loop changes it.
- **A frame read by `join` is read at the `T` of its `Task[T]`.** `__result` accepts a frame whose `__frame` call it can see, the call itself or a name that one call defined, and the frame that `finish` gives for the `number` of a value of type `Task[T]`, which it reads at `T`. That is sound because the field `number` is private to `std.task`, and only `spawn` makes a `Task[T]`, from the frame of a lambda that gives `T`. It refuses every other frame: "what this frame gives is not known here".
- **The state of the scheduler goes through each poll, and no frame saves it.** A scheduler is a handler of `task`, and what its operations use of the function it is written in, whether they assign it or not, is its state. `__poll(frame)` takes that state after the frame's address, of the scheduler in force where it is called, and gives it back first, and the poll of every function that suspends does the same: the function takes the state as its last parameters and gives it as its last results, after what it takes and gives of its own, as the state of any handler is passed to a copy. `System::Suspend` takes it after the kind and the handle and gives it back as the state the task goes on with, which is what the poll that resumes the task is given, so a child's `spawn`, `join`, and every wait it makes read and change the state the scheduler holds at that poll, and what the scheduler does to it while the task is suspended is seen by the task. A frame never holds it: the starter takes what the function takes of its own, and `suspend` saves no value of the state, so the state is never a second copy. One task runs at a time under a scheduler, so the state goes through the polls one after another. `suspend_frames` is given the types of the state, and a program has one scheduler that holds state: two that hold different state are refused as not built yet. The scheduler's names come last in the copies of the functions that run under it, in what they take and in what they give back, and in the function a lambda made a frame becomes.
- **A handler of an operation with type parameters of its own is checked in the function it is written in, with those parameters added after that function's.** The checker extends the function's scope, once for each handler, with the operation's parameters placed after its own, and checks each lambda against the operation's signature shifted to those places, so the parameters stand for themselves and for no type the function has. The lambda is checked once. The lowering runs a handler's lambda in place, so a call of the operation gives the lambda's environment the types the call is made at, in the places the check gave them, and the lambda is built once for each such call.
- **A frame under a handler that holds state is built, with the state through each poll.** A child under `fake_clock` of [Handlers](language/handlers.md) reads and changes the one state, which the function that polls takes last and gives last, as the scheduler's does, so no frame holds a copy. A function that polls, such as `std.task.run` under `tasks()`, is built under such a handler too. What is refused as not built yet is a handler that holds state installed under its own scheduler. A handler that holds nothing, and one that holds a value it only reads, is built as before. A group, `tasks()`, holds no state of its own.
- **A scheduler waits for the tasks that nothing names, for the library alone.** `quiet`, the third operation of `task`, waits until every task but the one that asks has ended: the scheduler's function for it waits for the first task of its chain that has not ended, with the wait that `join` makes, and asks again until none is left. A task whose handle was dropped is given back when it ends, so a scheduler keeps the frame of a task that another waits for until that one has gone on. A program that calls `quiet` is refused, since a program waits for a task by its handle, and the system's answer, where no group is in force, does nothing, as each child has run to its end where it started.
- **Exclusion is added only where tasks can meet.** When a task group opens under a handler whose operations assign a `mut`, the runtime makes those operations take turns. A handler with no tasks under it has no such cost.
- **A handler's state has a region of its own.** What an operation stores in the state of a handler whose state holds memory, as a list that it pushes onto, is not built in the stack of the child that called the operation, which is given back when the child is joined. The block that holds the call that installs the handler makes a region, which is a frame of the same make as a task's, with a stack that nothing else builds in, taken from the pool of [Memory of tasks](#memory-of-tasks), and it is one more name of the state, the address of its frame, which goes through each poll with the rest. Each assignment in an operation to a name of the state that holds memory says what it kept, with `RegionKeep`. The memory that is, or is held with, an address that is kept is built in the region, wherever in the function it is asked for, by the same groups that say which memory a function returns: a list that the operation built before the assignment, or that the caller built and gave to the operation, is built in the region, since a call that holds it with the list that is kept is in the group, and the call that builds it is given the stack of the region for its results, which its frame keeps from one request to the next. What is in no group with what is kept is built where it was, and so is what is in a group with it but is built where no frame of the region is made before, as the state of a handler that is made before the region is, which a function that writes `with listen(port: 80)` and `with routes()` one after the other has. The block that made the region gives it back where it ends, which is where the function the handler is written in may read its state last, and a `return` or a `break` that leaves the block earlier leaves it unreturned until the program ends: with `RegionFree`, or it moves it with `RegionMove` to the stack for results of the function when what the block gives holds memory, or an operation gave out memory of the state, so that what is read after the block is the stack of the region, with no byte copied. Memory of the state may also be kept by the state of a handler outside it that has a region, when an operation of that handler, or a function that runs under it, is given an address while the block runs, as `routes` gives the response its state holds to `send` of the handler that `listen` answers each request with. Then the block moves its region with `RegionMove` into the stack of that region, the outermost such, so that it is given back with it: not where its own block ends, and not where an arena around the block puts the stack of a task back. Where the program starts no task there is no pool, so the keeping and the giving back are not built, and the address of the frame is a null that nothing reads: a program that starts no task is built to the bytes it was.

## Memory of tasks

Tasks are not nested as calls are, so the two stacks of `alloc` cannot be the memory of a task: a stack put back by position frees what another task still holds, and a result built while the parent runs cannot be built in the parent's stack. A task's memory is regions of pieces that change owner, so a result is never copied, memory that one task frees is used by the next, and a task that holds nothing costs its frame and 64 bytes. This section says what is built, in the order it is built.

- **The pool is a block of memory that its address stands for.** It is a value of the state of `alloc`, made where a program that starts a task starts, passed to the functions that need it, and kept nowhere else, so a program has the pool of the code that runs it and no other. One task runs at a time, so nothing else touches it. It holds where the chunk being carved is, how many bytes of it are left, and the first free piece of each class.
- **A piece is of a class, and the classes start small and double.** The first holds 64 bytes, the next 128, and so on to 2 MB, sixteen in all, with 16 bytes of the piece spent on its header: its class and, while it is free, the next free piece of the class. A request is given the smallest class that holds it and its header, so a piece is never more than twice what it was asked for, with its header. A request that no class holds is asked of the system as it is, with its size in its header, and when it is given back the piece goes on a list of its own, from which the next request that no class holds takes the first piece that is at least as large as it asks for and at most twice, so that a task that ends, by failing too, gives its large memory to the next, and tasks that start one after another do not ask the system for more each time. Such a piece is never given to the system again while the program runs, as nothing is.
- **Pieces are carved from chunks.** The system is asked for 256 KB at a time, or for a piece when that is more, and a chunk is cut into pieces in the order they are asked for, so that the system is asked once for as many as 4,000 pieces of the first class. What is left of a chunk when a piece does not fit is not used again.
- **A piece given back is the next one taken of its class.** It is put at the head of the free pieces of its class, so what one task frees the next is given before the system is asked, and a piece is on one list at a time.
- **Why nothing in use is overwritten.** A piece is carved once, from memory that nothing else is given, and is given again only after `give`, which a task makes of a piece it holds no more. A piece on a list is not in use, and a piece taken from a list is removed from it first, so no two tasks hold a piece at once. What is written of a piece before it is given back is not read after, as the memory of an arena is not.
- **In a program that starts a task, the pool is a parameter.** Its address never changes, so it is passed as a value to each function that asks for room, makes a task, frees one, or calls one that does, and is never given back: it is not a stack, and no call swaps it. A program that starts no task has no pool and is built as it was.
- **Every stack grows from the pool.** A stack that has no room for a request takes a piece of the smallest class that holds it and its trailer, and at least twice what the piece it is in holds, so that a stack that grows doubles from where it is.
- **A task has two pieces to start, one for its frame and one for its stack.** `TaskFrame` takes a piece for the frame of the task, of the smallest class that holds it, and a piece of the first class, 64 bytes, for a stack for what the task builds, with its trailer at the end of the piece, which leaves 24 bytes for the first of what it builds, and the frame says where the stack is and where it started, which is the *origin* of the stack. The poll of the task runs on that stack, which its frame keeps from one poll to the next, and its caller's stack is given back as it was. A call of the task's own functions that wait are the polls of its chain, which take the stack from the one that calls them. A stack takes a bigger piece when it has no room, so a task that gives a text of twenty bytes holds a frame and 64 bytes, and a task that builds a list holds the pieces the list needs.
- **An arena in a task puts the task's stack back.** `with arena()` in a task notes where the stack is in the frame, as the token of an arena is no value that a poll that is run again can keep, and puts the stack back at the close, whether or not the block waits, since nothing else builds in the task's stack. A poll that returns at a wait puts nothing back.
- **A joined task gives its pieces back when its result holds no address.** `join` reads the result from the frame, and then `TaskFree` gives the pieces of the stack, from where it started, and the frame to the pool.
- **A joined task whose result holds an address is moved, and not copied.** `join` reads the result from the frame, whose addresses are into the task's pieces, and `TaskMove` makes a record of the stack at the top of the stack of results of the one that joins, where its free memory begins, of where the stack started and the bytes its first piece holds and the record before, and puts the record at the head of a list that the piece the stack is in keeps at its end, after the bytes it holds and the end of the piece after it. The frame is not moved: it is given back at once, since the result is read from it first, so what the joiner holds is only the stack the result is in. No byte of the result moves, so a join costs what it costs for a number whatever the size of the result. The pieces of the stack are the joiner's from here on, and are read where they are.
- **A put-back of a stack gives back what was moved in above the place.** A stack is put back at the end of an arena, at the end of a round of a loop that hands nothing on, and where a function returns the stack for temporaries it was given, and in a function that can reach a join the put-back is followed by `release_above`, which takes the records of the piece the stack is in that are at or above the place it goes back to, and every record of the pieces after it, and gives the pieces of the stacks they name to the pool, and those of the stacks moved into them, until none are left, with a list of the records themselves, each with its link in the place of the record before it. So a moved stack is freed at exactly the point where memory built in its place would have been freed, and the stack, which the put-back moves back, owns what is above it and nothing else. A function no join can reach puts its stacks back as it did.
- **A scheduler holds numbers and nothing else.** The queues of a scheduler are chains through four words of the header of each frame, which `__word` and `__set_word` of the library read and write by the number of a task, which is where its frame is. A handler of `task` builds nothing, since what it built would be in the stack of the task that called it, and that task may put its stack back or end. The frame is in a piece of the pool that is the task's until it is freed, so a task that is started in an arena does not lose its frame when the arena ends, and a scheduler takes a task out of its chain when `finish` gives the frame, before the frame is freed.
- **Why nothing in use is overwritten.** A piece is a task's until it is given back, and is given back once: by the one that joins it when its result holds no address, or by the put-back that passes below its record when it does. A record is made at the top of a stack, so every piece the stack has built above it is built after the move, and every piece below it before; a put-back to a place below the record is a put-back past everything built after the task was moved, and nothing alive is above the place it goes back to, as the stacks of [Memory a function gives back](#memory-a-function-gives-back) say. A put-back to a place above the record leaves the record, and the task, where they are. A task that is freed gives back the stacks that were moved into its stacks first, by the records at the ends of its pieces, so that a stack's pieces and what was moved into them go together, with a list in place of a call so that the depth of the tasks inside tasks costs no stack.
- **A handle that is dropped detaches its child.** Where a value that holds a `Task[T]` is dropped, the lowering sets a bit of the state word of the child's frame, which says that nothing will join it. A scheduler that starts a turn gives back, with `__drop`, which is `TaskFree` of a frame the library gives, the frame and the stack of each task in its chain that has ended and has the bit, and takes it out of the chain first. So a child that has ended when its handle is dropped is given back at the next turn, and one that has not is given back when it ends, and its result, which nothing reads, goes with it. A child that is dropped and still runs when its group's block ends is cancelled, as any child is.
- **Where a handle is dropped is found once, by the ownership check.** The walk of a body that `check/ownership.rs` makes knows, on each path, which names own a value that may hold a child, which is a type that holds a `Task` or a type parameter. A name owns what it is bound to, in a `mut`, a destructuring, a pattern of an arm, or a parameter that is taken, until a read gives it on: a read that is not a lend, which is a `join`, a call that takes it, a struct or a list it is stored in, the value of the block, or a read of a field of a child. What a name owns when it is not given on is dropped where it ends: at the end of its block, an arm, or a lambda, where a `break` or a `return` leaves it, where a `mut` is bound again, and where an arm or a loop's end is reached with a name that a path that meets it gave on, so that every path leaves a `match` or a loop with the same names owning. A value that is made and only looked at, as the result of a call whose value is thrown away, is dropped where it is made, and a list that a loop runs over, which is made where the loop is written, is held in a name of its own until the loop's block ends. A loop is read again from what is known at its head until that stops changing, and the sites of the last look are the ones kept. The check gives the sites to the lowering, by the address of the statement, arm, loop, or expression, and the names dropped there, with no type: the lowering drops a name only when its type in the copy it makes holds a child, so a program with no task is built as it was.
- **A value that holds children is detached by one function the compiler writes for its type.** `<detach[T]>` takes the scalars of a value of the type: for a `Task` it sets the bit, for a struct, a tuple, or an array it calls the function of each part that holds a child, for a list it calls that of its element for each element, and for an enum it switches on the case and calls that of the case's payload. A type that holds itself, as an enum that holds a list of itself, is followed by the function calling its own, however deep the value goes. A field that is given on, as `p.first` is by `join`, is not dropped with the rest of its name, which the name keeps as the fields that were given on, and an assignment to a field drops the field it replaces. A loop over a list ends in two ways that the lowering tells apart by the `Flow` that `each` gives, so what a `break` gave on and the end of the list did not is dropped where `each` is over. **Not built yet:** an element of a list, or a part of an enum's payload, that is given on while the rest is dropped: a loop that gives an element on gives the whole list on, so the elements it does not join are not detached, and neither is a name kept in a frame as an array. Each keeps its child's memory until the program ends, and none is freed twice. The scheduler of the system that does not wait, which runs a child to its end where it starts it, gives nothing back either.
- **A task that is cancelled is ended by the end functions of its suspension points.** Each suspension of a function that suspends has an end function, which the compiler writes for exactly the values alive there that own something and ends each as its owner does: a value bound by `with` is closed by its closer, a handle of `fs` or `net` by its handler, a child by cancelling it, and any other value that holds memory by its drop. The values that are alive at a suspension are those the pass `suspend` saves in the frame, and the ownership check says which of them own, as it says where a handle is dropped, so the end function is a path that the walk of the body already knows, taken from the state the frame says. Cancelling a task cancels its own children first, in the reverse of the order they were started in, then runs the end functions of the chain of the frame, the innermost callee first, and then gives the regions of the task back, so that every value is ended exactly once and the frame is not read after. A task that is running and not at a suspension is cancelled at the next one, and a task that never suspends is not.
- **A task is asked to end by a bit of its frame, and each function it is in reads it from its own frame.** The scalar form has `System::Cancelled`, which takes nothing and gives a 64-bit integer, 1 once the task has been asked to end and 0 until then. The scheduler asks by setting the bit `CANCEL`, 64, in the second of the four header words that it keeps its queues in, in the frame of the task, and polls the frame again; the bits below it are the scheduler's own (ended, waits for a task, for a descriptor, detached, waits for a time, woken by its time). The pass `suspend` reads the bit from the function's own frame, and the poll of a function that calls one that suspends writes the bit into the header of the callee's frame each time before it polls the callee, so every function the task is in the middle of sees it, whatever its depth, and the poll takes no more parameters and gives no other status: a request word in the frame's header is the simpler of the two ways, since an extra parameter would change the poll on every target. In a function that is not made a state machine it is the constant 0, so a program that starts no task has none of it left and is built as it was. The lowering writes after each call that may suspend, and after each wait, `if Cancelled { what the function owns and has not handed on is ended, and the function returns }`, which is the same drop site as a `return` and gives zeros for what the function gives, which nothing reads because its caller takes its own exit as soon as the call returns. A closer or a drop on such an exit that may suspend is refused where the program is compiled, since an exit that suspended would not end the task. The exit is written by `finish_call` after a call of a copy that may suspend, which is a copy that carries `net`, `time`, or `task` under a scheduler, or that polls, and after a lambda that is lowered in place and wrote one, so that the function that runs the lambda leaves too; in the block of a loop over a value the exit answers `.stop`, or sets what a `return` in the block keeps and answers `.stop`, and the function leaves after the loop, and a block that calls a function that carries one of those effects is a block that can answer `.stop`, so `each` tests what it gives. The exit drops what the function owns at that call, which the ownership walk records as the site `Cancel` of the call, as it records `Leave` for a `return`. A child the function holds is not detached there but asked to end through its handle: the bit that asks, with the bit that detaches, is set in the frame of the child, which stays in the pool until the scheduler has polled it. So a parent that ends asks its own children first, each is polled by the scheduler as a task that is asked to end is, and a child never reads a frame the scheduler freed: the frames of the tasks that have ended are freed by `reap`, only when the handle was dropped, and by the end of the block, once every task has been polled. When the block of a scheduler ends, the scheduler asks each task still in its group that has not ended, and polls each that has run, the one started last first, so a child ends before the task that started it; a task that never ran is polled too, and the function of its lambda begins with the same look for the request, which ends what the lambda was given and returns, so that a task asked to end before it ran does none of its work. A task asked to end that waits again is a failure of the compiler, and the scheduler says so and ends the program. A handle of `net` or a `File` of `fs` that the function owns, or that a struct, a tuple, an array, an enum, or a list it owns holds, is ended there by a call of the operation that ends it (`close`, `stop`, or `unbind` of `net`, `close_file` of `fs`) through the handler in force, which is the same call a program makes, so a test's handler counts it; the ownership walk finds the handles as it finds the children, and refuses a function that owns one across a call of a function that carries `net`, `fs`, `time`, or `task` and does not carry the effect of the handle itself, since no handler could be called from it. Nothing is kept for it at run time: a task that is never cancelled pays for none of it. A value of a type with no `Discard` that a task owns when it ends goes with the task's memory, as [How a task ends](language/task-ending.md#what-happens-in-each-case) says.
- **A parent ends its children through the handles it holds.** A cancel exit that owns a `Task[T]` cancels the child it names, by asking it to end and polling it, before it ends anything else the function owns, so each value is ended once, by its owner, and nothing reads a frame after it was freed. The scheduler at the end of a block cancels only the tasks that no task alive holds a handle to, the newest first, and gives the frame and the stack of each back after the poll that ended it. A test that frees a frame writes over it first, so a read after the free fails the test and does not pass by luck.
- **A failure ends the task and not the program.** A request for memory that the system refuses, and a write to the console that it refuses, are the instruction `Fail`, which takes the failure as a 64-bit number, 0 for the memory and 1 for the write, and ends the task that runs it. The poll of a task gives a third status, `failed`, beside `done` and `waiting`, with the failure in the place that the handle of a wait is in, and `Poll` of `std.task` has a third case, `failed: u64`. A `Fail` in a task that a scheduler polls goes back to the innermost scheduler poll that is running, which gives the status `failed`; anywhere else, in a program with no scheduler or in the program's own `main`, it ends the program with the status 1, as a refused request for memory does, and the root task is `main`, so a failure that reaches it ends the program with a failing status. The evaluator answers `Fail` by an `Err` that the innermost `<poll any>` call catches. **Built:** the instruction, the third status, and the evaluator's answer; on x86-64 and arm64 the native unwinding of the next bullet, for a program that has a poll and a function that fails or asks for memory, and for each scheduler of `std.task`, which ends a task that failed as one that ended and goes on; each other native target ends the program on `Fail`, and each scheduler ends the program when the task that failed is its first. A write to the console that the system refuses is the failure 1, by the same routine, on x86-64 and arm64. A task that failed ends what it owns at each call the failure went up through, by the landings of the bullet below. **Not built:** WebAssembly, which has no way to put a stack back, so there a failure traps and the program is the one task.
  - **The unwinder reads a table, and no frame is changed.** Neither backend keeps a frame pointer, a frame has one size for the whole function, and each function's callee-saved registers are saved at places that are known when it is compiled. The table is in the data section, keyed by the range of addresses of each function: the size of its frame, the registers it saved and where, and where its return address is. On a failure the unwinder starts from the return address of the call that failed, finds the function that holds it, runs the cleanup of that call site if it has one, puts back the registers that function saved, and goes on to its caller, until it reaches the poll. A call site has a cleanup when the function owns something to end there, a handle of `net` or a child, which is `Site::Cancel(call)` of the ownership check, so a call site that owns nothing has no entry and the path that does not fail pays for nothing. A cleanup closes through the handler in force and asks for no memory; a handler that asks for memory while it closes during a failure of memory is a second failure, and ends the program with a failing status. **As built on x86-64 and arm64:** the table holds, for each function, where it starts and ends, the code of its own that puts back its callee-saved registers from the frame whose base is in rax and gives the frame's size in rcx, and the place a failure goes on at when the function is a poll, which is that code when it is not. A failure is a call of one routine with the failure in a register (r11 on x86-64, x29 on arm64, which nothing else uses), so that the return address names the function and the place that failed, and a refused request for memory is the same call from the end of the function that asked. The routine finds the function that holds each return address, puts back what it saved, and goes to its caller, until the function is the poll, whose own epilogue it goes to with the stack as the poll had it, after the poll's results are given as the status 2, the failure, and zeros. A return address that no function holds is the start of the program, which ends with the status 1. A program with no poll, or with nothing that fails or asks for memory, has none of it. **A failed poll gives back what it was given.** The poll of a task passes the state of the handlers through, and a failure takes the frames that held what the task changed. The poll keeps in its own frame what it was given to pass through, a pass of the compiler leaves its parameters and results as they are so that each result is where its parameter was, and the landing gives each result its parameter's value, so the state is as it was before the poll: the memory a handler of `alloc` passes, and the rest. **The scheduler keeps its chain in memory too.** The head of the chain is what a task changes when it starts a child, and the poll gives it back as it was, so a task that started a child in the poll that failed would lose the child. A group makes one spare frame, which holds the head in its first header word and which it drops at the end of its block: `start` and `finish` write the head there each time they change it, the scheduler writes it before each poll, and after a poll that failed it reads the head from it and takes the other state it keeps in its handlers from what it holds itself. The header of a frame is as it was, and a task pays nothing. It is not a word of each poll's record, because `start` and `finish`, which change the head, run inside the frames of the task that may fail and reach a place only by a number that is handler state, and a word of the poll's own stack frame has no such number. **A landing is written for each call that the function owns something across.** The call is followed by a choice on a new instruction of the scalar form, `Unwinding`, which gives 0 and is never taken, and whose first jump goes to the landing: the blocks that end what the function owns at that call, which are the ones that the exit of a task that is asked to end writes, from the same generator, so a failure and a cancellation end the same values at a call, and then `Resume`, which goes on up. No pass can know the jump is not taken, so what the landing reads is live across the call, and the allocator keeps it where a call keeps a value. A call that has a landing is replaced by its callee's blocks as any call is, and the landing goes with it: each call among the callee's blocks that has a landing of its own ends what its function owned and then goes to the landing of the call that was replaced, with the values that landing is given, and each call among them that has none is followed by a choice on `Unwinding` whose first jump goes to that landing, so every call that is left in the code has one landing, which ends everything that was inlined around it. A request for memory, a write, and a `Fail` that the system may refuse are failure sites as a call is: when one is among a callee's blocks that replace a call that has a landing, it is followed by the same choice on `Unwinding`, so that a failure that starts at it goes to the landing of the call that was replaced, and a callee that holds one is replaced like any other. On x86-64 and arm64 such an instruction has a way in of its own and no row of the table: a refusal jumps to code that gives its failure, 0 for memory and 1 for a write, and goes on in the way in to the landing, with the stack as the function has it, and a `Fail` jumps there with its failure. The evaluator runs the landing that follows the instruction that failed, as it runs the one that follows a call. What a function owns at one of these instructions that no call was replaced by, and nothing follows, is not ended by a landing. A function that owns nothing at a call has no landing there, and a path that does not fail pays for none. On x86-64 and arm64 the table of the unwinder has a second part, from the return address of such a call to a way in to its landing, which keeps the failure in a slot of the frame, and the unwinder looks there first for each frame, a poll's too, before it puts the frame's registers back; `Resume` reads the failure from the slot and puts the registers back by the frame's own code, or goes to the poll's landing when the function is a poll. A landing is entered with the stack as the function had it at the call and the registers its callees had put back. The evaluator enters a landing by making the choice on `Unwinding` take its first jump once, as the frame goes on from the call, and runs it to `Resume`. A landing is made by the same drops as the exit of a task that is asked to end, so a closer that may suspend is refused where it is compiled, as there; one that asks for memory or writes while a failure goes up fails a second time, and that ends the program with a failing status. **A task that failed is marked, and a join of it fails the joiner.** The state word has a bit for it, and the word the task waits on, which it waits on no longer, holds the failure. A task that ended by a failure never made the value a `join` gives, so `join` ends the task that joins it by the same failure, with the instruction `Fail` that only the library may write as `__fail`, and `outcome` gives `.err` of the `Failure` and frees the frame, so the joiner goes on. A failure that reaches the root task ends the program with the status 1. The evaluator answers a request over its limit as the system does, with the failure 0.
  - **The scheduler's poll leaves a record.** Each poll that a scheduler makes writes a record on the stack, in the frame of the function that polls, and the program holds the address of the innermost one in a word of its static data, putting the one it replaced back when the poll returns, so that a poll inside a poll nests. The record holds the stack pointer of the call, where the poll goes on, and the head of the scheduler's chain of tasks, which `start` writes where it assigns the head, so that a child that a task started in the poll that failed is in the chain after it. After a poll that gives `failed` the scheduler reads the head from the record and not from what the poll would have given, which the unwound frames took with them, and ends the task as a cancelled one.

## Structure

The compiler is a pure function from a set of roots and the source text to results: diagnostics, types, and optionally a binary. Nothing is kept between runs, so every run starts clean and no result can be stale.

It works in three steps, each a pure function of its inputs with no shared mutable state.

1. **Parse** a file. This depends on that file's text alone.
2. **Collect signatures** from the parsed files.
3. **Check a body** against the signatures. A signature states everything a caller needs, so checking one body never depends on another body, and bodies check in parallel.

The compiler is lazy. It starts from the roots and does only the work they reach. A module is a file named by its path, imports are explicit lists, and a trait implementation lives with the trait or the type, so the compiler finds a name's file without scanning the project. Files that nothing reaches are never read.

| Command | Roots |
| --- | --- |
| `smith build`, `smith run` | `main` |
| `smith test --name x` | That test |
| `smith test` | Every test |
| `smith check` | `main`, every test, and a library's public items |

- `smith run prog.smith one two` gives the program the words after the file's name, `one` and `two`, as the words it was started with, whatever they look like, so a flag among them is the program's and not the compiler's. A flag before the file's name is `smith`'s or the command's, as [Where a flag goes](language/command-line.md#where-a-flag-goes) says. `smith build` takes no words. The words are given as the system gives them, whatever bytes they hold, so a word that is not valid UTF-8 ends the program as it ends the executable, with the same output and status. An argument of the compiler's own, such as the file's name, that is not valid UTF-8 is an error in the usual form, and `smith` never ends in a panic over its arguments.
- Checking a body needs only the signatures of what it calls. Running it needs those bodies too, all the way down.
- Code that no root reaches is not compiled, so it can hold an error while a single test runs. That lets a new design be tried with one test before every caller is updated. The error surfaces when a command whose roots reach it is run.
- `grad(f)` needs the body of `f` and of everything it calls. Its type depends only on the signature of `f`, so checking stays local, and whether `f` can be differentiated is decided when the code is built.

### Keeping nothing of an older Smith

Smith has no users but its authors, so a change to it removes the old form everywhere in the same pull request: from the parser, the checker, the lowering, the backends, the library, the tests, `compiler/`, `measure/`, the skills, and `knowledge/`. No code, error, fix, test, or page knows what was there before.

- No error or fix recognises a spelling, keyword, name, or command that was once Smith and no page of `knowledge/` has now, to say what replaced it. A mistake that a reader of `knowledge/` could make, such as a missing `take`, is still refused and explained.
- No alias, second name, or second spelling is kept so that older code builds, and no function of `std/` is kept for that.
- No branch, function, field, or case of an enum is kept that no program the grammar allows reaches.
- No test checks a behaviour that `knowledge/` does not have.

A form is old when it was once Smith and no page of `knowledge/` has it now. What a page of `knowledge/` has and the compiler does not build yet is not old.

### Errors and warnings

An error stops every command. A warning is reported only by `smith check`, which fails if there are any, so it is the lint step and a continuous integration run needs no extra flag.

What the compiler prints is written to be read by a model, and there is one form of it, for an error and for a warning alike. An error gives its place, what is wrong, the line of source with a mark under the place, and what to write when the compiler knows.

```
hello.smith:1:13: `print` needs the `console` effect, which `main` does not declare
  1 | fn main() { print("hi") }
    |             ^
  fix: write `fn main() <console>`
```

- The first line is `file:line:column: message`. Lines and columns count from 1, and a column counts characters.
- The line of source is shown as written, except that a tab is shown as a space and any other control character as `�`. The mark is placed for a terminal, where a wide character takes two places. Advice is only ever on the `fix:` line, and an error with none has no such line. An error whose message is the author's own words, as the comment above a `requires` is, shows what was to be proven on a `goal:` line under the message, and every other error has no such line.
- Every error in a file is reported, each once, in the order of their places, so one round of changes can fix them all.
- A file is read in stages: its text, which must be UTF-8 with no carriage return, then its tokens, its syntax, and the check. Only the errors of the earliest stage that finds any are reported, because each later stage reads what the earlier ones produced.
- What is not built yet is no mistake of the file, so it does not stop the stages. The syntax stage reads past an expression, a statement, or a type that is not built, such as a float, an array type, `+=`, or a function type with effects, and keeps its place with a value of no type. The check reports it with the file's other errors, each once at its place, and says nothing of what that value gives: a binding of it, a call that takes it, and an operation on it are not checked, and a name that a statement not built would have bound is still bound. A definition that is not built, such as `effect`, `foreign`, `derive`, or a contract in a trait, is not read past, as the names it defines are not known, and it is reported with the errors of the syntax.
- An error that another error explains is not reported. A mistake in the syntax hides the rest of its statement, or of its signature, and a listed effect with no such name hides a missing effect, which it may be a misspelling of. A listed effect that the file does not import is the one error of the missing import, and no error says the effect is undeclared. A function that lacks an effect is told so once, at the first call that needs it, and nothing is reported about what a call of a function that does not exist gives.

- Dead code, meaning a definition no root reaches, whether a function, a struct, a trait, or an implementation, is a warning at its name.
- A binding whose name is never read is a warning at the name, and so is an unused import. A parameter is not a binding.
- A warning is printed in the form above, with a `fix:` line when the compiler knows what to write. Warnings are reported only when there is no error, every one of them, in the order of their places.
- An unused value whose type cannot be discarded is an error, as [Ownership](language/ownership.md) requires.

### Commands that report

The command line is the compiler's interface for people and for agents, and its output is plain text in the one form above.

| Command | Reports |
| --- | --- |
| `smith check` | Errors with a counterexample, the remaining proof goal, and candidate fixes, plus warnings |
| `smith hole` | The type, effects, and proof goal a `hole(name)` needs |
| `smith find` | Definitions matching a type signature, so existing code gets reused |
| `smith deps` | What a definition uses, and what uses it |
| `smith cost` | Allocation and operation counts as formulas over the sizes, and which arrays were stored |

## Representation

The pipeline is the classic one: tokenize, parse, collect signatures, check, lower, run the passes over the scalar form, and emit. A run that only checks stops after the fourth step.

The lexer and parser are hand-written: recursive descent for declarations and a Pratt parser for expressions. One syntax tree serves the checker and the formatter. Every node keeps its source span, comments are ordinary nodes attached to what follows them, and an error node holds any tokens the parser skipped, so broken programs and holes are still representable.

| Level | What happens there |
| --- | --- |
| Surface tree | Parsing and formatting |
| Typed core term | Checking and `grad`. About ten node kinds |
| Kernel form | Fusion, contractions, and vectorization. Shared by the CPU backend and both GPU emitters, which leave from here |
| [Scalar form](#scalar-form) | Inlining, folding, sharing what is worked out twice, and the removal of dead code. The same for every chip |
| Machine form | Instruction selection and register allocation, for one kind of chip |

### How a whole number is kept

Today the compiler keeps a whole number as itself, in the smallest of 8, 16, 32, 64, and 128 bits that holds every value of its range, signed when the range has a negative value, so a range is the size it is kept at and no smaller. A range of 65 to 128 bits is two integers of 64, the low one first, and is built for `+`, `-`, `*`, `/`, `%`, the comparisons, `narrow` and `clamp`, and its digits in `Fmt`; a result that needs more than 128 bits is refused. A range as the distance from its least value is planned.

A whole number is a range, and how it is kept is the compiler's choice, which no program can observe. The choice has three parts.

- **The size is the smallest of 8, 16, 32, 64, and 128 bits that holds the number of its values.** The number of values of `a..b` is `b - a`, whatever `a` and `b` are. A range of 128 bits is two integers of 64 in the scalar form, the low one first, so the form has no wider integer: a sum is an add and an add with the carry, a product of two integers of 64 bits that are both signed or both not is the instruction that gives both halves, which is `mul` or `imul` of one operand on x86-64, and `mul` with `umulh` or `smulh` on arm64, and dividing by a power of two takes a half or shifts across the two. Dividing by any other number calls one function of the runtime, written once in the scalar form, which takes the bits of the number from the top and subtracts the divisor where it can, 128 rounds on every target; a signed number is divided by its size, and the quotient is negated where the signs differ and what is left over where the number divided is negative.
- **The form is as itself when that size holds its values as they are,** signed when the range has a negative value, **and as the distance from its least value otherwise.**
- **A bound that is not a constant,** as the `n` of `0..n`, is kept at the size of the type of `n`.

| Range | Takes | Is kept as |
| --- | --- | --- |
| `0..101` | 1 byte | Itself |
| `-5..6` | 1 byte | Itself, signed |
| `1000..1010` | 1 byte | The distance from 1000 |
| `1900..2100` | 1 byte | The distance from 1900 |
| `0..256`, the `Byte` | 1 byte | Itself |
| `0..18446744073709551616`, the `Nat` | 8 bytes | Itself |
| `0..340282366920938463463374607431768211456` | 16 bytes | Itself, in two words |
| `-9223372036854775808..9223372036854775808`, the `Int` | 8 bytes | Itself, signed |

Kept as a distance, copying, comparing, matching, and adding cost nothing, and subtracting, multiplying, dividing, and passing to a range with another base cost one addition of a constant. A range that fills a size exactly is always kept as itself, so a foreign declaration, which is written with those ranges, passes its values as they are.

## Hashing

The `Hash` a type is given is built from one function over 64 bits and a rule for each kind of type. It is lowered to the scalar form, so the evaluator and every target give the same number, and no run of a program changes it.

- **The function is the finalizer of MurmurHash3 for 64 bits,** `mix`: xor with the value moved down 33 bits, multiply by `0xff51afd7ed558ccd`, the same xor-shift, multiply by `0xc4ceb9fe1a85ec53`, and the same xor-shift once more. It was chosen because it takes every 64-bit number to a different one, so no two numbers are lost, and moves each input bit to about half of the output bits, so the low bits of a hash, which a table reads, depend on every bit of the key. It costs three shifts, three xors, and two multiplies, with no table, and its two constants are all it holds.
- **A whole number** is widened to 64 bits, by its sign when it has one, and mixed. **Text** is hashed over its bytes by FNV-1a, which costs one xor and one multiply for each byte and is the fastest hash of short keys that has no table, and the result, with the size, is mixed, since FNV-1a alone leaves its low bits weak.
- **A struct or a tuple** starts from 0, and for each part takes `mix(h * 0x9e3779b97f4a7c15 + part)`, where `part` is the part's own `Hash`. **An enum** does the same from the number of its case and then, for a case that holds something, what it holds, so two cases that hold the same value hash differently. **A list** does the same over its elements, and then its size. A multiplier that is odd takes every `h` to a different number, so the order of the parts changes the hash.
- **A type's own `impl`** replaces its given one wherever it is a part, so a struct that holds it is hashed with that.
- A test draws 1000 different values of each kind of type, from numbers that differ by a drawn odd step, and checks that no more of them share the low 16 bits than four times what chance leaves, which is about 8.

## Backends

| Target | Output |
| --- | --- |
| CPU | arm64 and x86-64 machine code, written to Mach-O, ELF, and PE directly |
| Apple GPU | Metal shading language source, compiled by the OS at load time |
| Vulkan GPU | SPIR-V binary |
| WebAssembly | A module, and a file of JavaScript that loads it |

Everything up to the kernel form is the same for every target. Each CPU target supplies its instruction selection, its calling convention, and its executable writer, and that seam exists from the first program. The compiler writes executables itself and runs no linker or assembler.

A target is one case of an enum, and adding a case is what adds a target: the compiler then requires every place that depends on the target to handle it. A target has one name, which is its case in the `Target` enum that `build` takes in `project.smith`, and the same word selects it on the command line, as in `--target linux_x64`.

- **Linux on x86-64,** named `linux_x64`. A static ELF executable that talks to the kernel directly.
- **macOS on arm64,** named `macos_arm64`. A Mach-O executable that reaches the kernel through the system library, which it links dynamically, and that carries the ad hoc code signature Apple silicon requires.
- **Linux on arm64,** named `linux_arm64`. A static ELF executable that talks to the kernel directly.
- **macOS on x86-64,** named `macos_x64`. A Mach-O executable like that of `macos_arm64`, for an Intel Mac.
- **Windows on x86-64,** named `windows_x64`. A PE executable for the console that reaches the kernel through `KERNEL32.dll`, which it links dynamically.
- **Windows on arm64,** named `windows_arm64`. A PE executable like that of `windows_x64`, for an arm64 machine.
- **WebAssembly,** named `wasm`. A module of 32-bit WebAssembly, written by the compiler as the executables are, and a file of JavaScript beside it, with what [The host of a WebAssembly module](#the-host-of-a-webassembly-module) says. `smith build --target wasm hello.smith` writes `hello.wasm` and `hello.js`, and `node hello.js` runs the program. It is built for programs whose effects are `console`, `entropy`, `fetch` through `host`, and `alloc`, and `smith run` does not run it.

A function of a WebAssembly module has the locals it needs and no more: each value has the local of one of its kind that is dead where it is made, by the places each is alive in, taken from the first to the last, so the locals of a function are the most values of each kind alive at once, and not how many values it makes. An engine takes about 50,000 locals in a function, parameters among them, so a function that needs more is refused when it is built, with one error that names the function and the limit, and no module is written that does not load.

Every target builds floats. WebAssembly has the instruction for each of the form's, with `f32` and `f64` as its own types: a float is a local of its type, a read and a write of one are `f32.load` and `f64.load` and their stores, a negation is `f32.neg`, a comparison gives an integer of 32 bits as the form's of 8 does, a float from a whole number is `convert` and a whole number from a float is the `trunc_sat` that saturates and gives 0 for a float that is not a number, held to the range of a size below 32 bits by a choice. It has no fused instruction, as the one that relaxed SIMD has may or may not fuse, so `Target::emit` takes each fused instruction of a program for it apart into a call of one function of the scalar form for each size, `scalar::unfuse`: the product and the sum are worked out exactly with whole numbers, of 106 and of 128 bits and a bit that says whether any was left below, and rounded once, to the nearest, ties to even, with gradual underflow and an overflow to infinity, so that the bits are those of the fused instruction of every other target. A product with a float that is not a number, an infinity, or a zero among its operands is worked out by the instructions of floats, which give those results exactly, but for an infinite or not a number addend with a product that is finite and too great for its size, which is the addend. The targets for x86-64 and arm64 build vectors. WebAssembly does not: as `Target::builds_vectors` says, it stops when given a program with one, with one message that names the first function that has it.

Targets share what they have in common: the arm64 instructions are written once for every arm64 target, the x86-64 instructions once for every x86-64 target, the ELF writer once for both Linux targets, the Mach-O writer once for both macOS targets, and the PE writer once for both Windows targets.

Everything runs as native code, including compile-time code such as literal conversion. The checker contains a small symbolic evaluator that simplifies expressions with unknowns, such as `n + 0`, to compare types. It defines what core terms mean, so it is also the test oracle.

### The instructions a chip must have

The instructions a program uses are chosen when it is built and never while it runs. No executable tests its chip to pick between two versions of a loop: such a test costs a jump at every call, keeps the loop from being lowered in place, and builds it more than once.

- **An executable for x86-64 needs the level `x86-64-v3`,** which has AVX2, the fused multiply and add, and the bit instructions that came with them, and which the chips made since about 2015 have. Vectors of 256 bits and one instruction for `a * b + c`, which [The rules floats keep](language/float-rules.md#a-product-is-fused) asks for, are there on every chip the executable runs on, so a float gives the bits it gives on arm64, which has always had both. No executable is built for a lower level.
- **An executable for arm64 needs NEON,** which every arm64 chip has, with its fused multiply and add.
- **An executable checks its chip once, before `main`.** One that is started on a chip without what it was built for stops with a message that names what is missing, and runs nothing else. This is the only test of the chip in a program.
- **A higher level is a choice of the build.** AVX-512 on x86-64, and SVE on arm64, are for a program whose author knows where it runs. A project that serves several levels builds an executable for each, and what installs it picks one.
- **WebAssembly has one set of vectors,** of 128 bits, and no levels.

The check is built for the three x86-64 targets, as the first code of the executable, after the system gives the program its words and before `main`. It asks `cpuid` for each of FMA, MOVBE, F16C, AVX, XSAVE, BMI1, AVX2, BMI2, and LZCNT, which together are the level, and `xgetbv` whether the system has turned on the registers of AVX. The first that is missing ends the program with status 1 after one line on the error output that says the level and the feature, and nothing of the program runs. Its cost is the same few dozen instructions for every program, once. arm64 and WebAssembly have none. This is planned for the rest: today an executable for x86-64 uses SSE2 and nothing above it but the instruction of FMA that a fused product is and the one of SSE4.1 that a rounding to a whole number is, as [Scalar form](#scalar-form) says, and no higher level can be chosen. An executable for arm64 fuses a product as its chip does.

### The host of a WebAssembly module

The module and the file of JavaScript are built for programs whose effects are `console`, `entropy`, and `alloc`. A handler that is a host, and a module that suspends itself, are planned.

- **An effect is an import.** A WebAssembly module has no operating system under it, and what it may ask of its host is what the module imports. Each operation of an effect that reaches `main` with no handler is an import of the module, named for the effect and the operation, and `main` is an export. So what a module can do to the world outside is its list of imports, which is the list of effects `main` carries, and a module whose `main` lists none imports nothing. An effect a program declares is an import in the same way as one of the library's. Four imports are built. `console.print` takes the stream, as 1 for standard output and 2 for standard error, the address of the bytes, and how many, and a module has it exactly when the program writes to a stream. `entropy.fill` takes the address of the bytes and how many, fills them with bytes nobody can predict, and gives 0 when it did and another number when the host refused, and a module has it exactly when the program asks for random bytes; the program says that the system gave no random bytes and ends with status 1 when it is refused. `fetch.send` takes the address of a request and how many bytes it has, and gives how many bytes the answer has, or a number below 0 when no server was reached (minus 1) or the host could not ask (another number); `fetch.take` takes the address of that many bytes and fills them with the answer. The request is the host, the port, and the most bytes of body, each ended by a line feed, and then the request as it is written on the wire; the answer is what the server wrote, until it ended its connection or until it wrote more than the module reads. A module has the two exactly when its program installs `host()` of `std.fetch`. The host of `node` makes the request with a child process of its own, which the call waits for. A program with an effect the compiler does not build is refused with the one error that names the effect, as for every target. A program that calls `input` of `console` is refused with one message, as the module has no import for reading yet.
- **The compiler knows no host.** Nothing in it names a browser, a server, or a company's platform. Beside the module, `smith build` writes a file of JavaScript that loads it and supplies each import the module has, from the list of them, which is what a host with a JavaScript entry needs, as a Cloudflare Worker has. What a platform offers beyond the library's effects, as its storage, is an effect declared in a library, and reaches the host as any other. A host that speaks another interface, as WASI, is given the same module with an adapter that supplies the same imports. The file of JavaScript is for `node`, which reads the module beside it, writes what the module prints with `fs.writeSync`, and answers `entropy.fill` with `crypto.getRandomValues`, which takes at most 65536 bytes, so in pieces of that size.
- **A handler is a host.** A program that runs a WebAssembly module supplies its imports, and in Smith what supplies the operations of an effect is a handler. So a Smith program that runs a Smith module handles the module's effects with handlers, and grants it the effects it chooses.
- **A module suspends itself.** An import that must wait, as a request to the network, cannot return what it waits for, since a host with JavaScript gives a promise and an import returns at once. The copy of a function that runs under such an import is the state machine [Effects](#effects) describes: it saves its place and returns to the host, and the host calls the module's export `resume` when what it waited for is there. The module asks nothing of the engine for this, so it runs on every engine, and it is the same code that suspends a task on every other target.

- **Memory is the module's own.** A module has one memory, which it exports. The program's texts are in it from address 16, in one data segment, so no text is at the address that holds nothing, and the memory the program asks for begins after them, at a multiple of 16. A request for memory, which is the call into the system that asks for it, is a function of the module and no import: it gives the next free bytes, and when they pass the end of the memory it grows it by the pages that are missing with `memory.grow`. A request that the engine refuses, and one of 2^32 bytes or more, ends the program with status 1, as a request the system refuses does on every target. The module is never given memory back, as no other target gives it.
- **A size is 64 bits and an address is 32.** An integer of 8, 16, or 32 bits is an `i32` held with zeros above its size, one of 64 bits is an `i64`, and an address is an `i32`. In memory an address takes the 8 bytes the scalar form says, its high four bytes 0, so a list, a text, and a struct are laid out as on every other target. A number of 64 bits that moves an address, or counts the bytes of a write, is taken as its low 32 bits, which is as far as an address reaches. A number of 64 bits that asks for memory is not cut: when it is 2^32 or more the request is the one that ends the program.
- **A function's blocks are written as the engine's own `loop`, `block`, `if`, and `br`.** The engine optimizes what it can see, and a loop that it sees is one it optimizes, so no function is written as a loop that chooses its next block by a number. A block that jumps are made back to is the start of a `loop`, and each jump back is a `br` to it. A block that more than one jump reaches, not counting jumps back, is where a `block` ends that holds the code of everything that jumps to it, and each of those jumps is a `br` out of it. A block that one jump reaches is written where the jump is. A choice between two jumps is an `if`, or a `br_if` when one of the jumps gives its block nothing and leaves a structure that is open, so a loop's test and its exit are one `br_if`. A choice between more is a `br_table`. This is what Ramsey's "Beyond Relooper" does with the tree of dominators, and it covers every function in which each jump back goes to a block that dominates it, which are the loops the passes leave. The passes never make another, and a test says so for every generated program and for the lexer. A function the scalar form can still make in which one is another, as two blocks that jump to each other and are both entered from outside, is written as a loop over a number: the number of the block to run is a local, the code of each block follows a `br_table` that goes to it, and a jump sets the number and goes back to the top. It is right for every function and no faster than it was, and a test runs one.
- **A value is a local, and a block given a value by one jump takes that value's local.** Each value has a local of its own, which the engine puts in a register as it sees fit. A parameter of a block that exactly one jump reaches, and that is not the start of a loop, is the local of the value that jump gives it, since the value is alive wherever the block is, so that jump copies nothing. Any other parameter is a local that each jump sets, as if all were copied at once, and a jump sets none that already is the value it gives. An instruction reads its operands from locals and sets its results to locals, and none is kept on the engine's stack for the next instruction.
- **The end of a program is the module's `main` returning, or a trap that leaves a status.** `main` is the export the host calls, and the program's own `main` is called from it, with the program's name as the only word when it takes the words. The call that ends the program with a status keeps the status, which the export `status` gives, and traps, since no function that calls it could otherwise be left. The host reads the status, and a trap that left none is a failure of the module that it does not hide.

## Standing alone

A Smith executable carries everything it runs. All of its code is compiled from Smith source into the one file, in the same way that outside code is [vendored](language/dependencies.md) into the project and never fetched from a shared cache. The only thing the executable needs from the machine is the operating system's own stable boundary, and that boundary is the kernel wherever the kernel allows it.

| System | Boundary | Why |
| --- | --- | --- |
| Linux | The kernel's system calls, made directly | The kernel keeps them stable, so the executable is fully static and uses no C library |
| macOS, iOS | `libSystem`, loaded by the system's dynamic loader | Apple changes system call numbers between releases, and Apple silicon does not run a static executable |
| Windows | `KERNEL32.dll`, loaded by the system's loader, `bcryptprimitives.dll` for random bytes, and `ws2_32.dll` for the sockets, which only a program that carries `net` asks the loader for | Windows changes system call numbers between builds, and its sockets are in Winsock, as the other way in is `ntdll`'s AFD device, which is undocumented and may change in any build |

- From a system library a program calls only the thin wrappers over the kernel, such as `write`, `read`, `mmap`, and `exit`, or on Windows `WriteFile`, `ReadFile`, and `ExitProcess`, and for random bytes `getentropy` on macOS and `ProcessPrng` on Windows. It never uses the C library behind them. Allocation, formatting, and everything else are written in Smith and behave the same on every target. Reading standard input is the one place they differ: `ReadFile` reports a closed pipe as a failure, so on Windows a read that fails is the end of the input, and elsewhere a read the system refuses ends the program with a failing status.
- The network is built for Linux, macOS, and Windows, and the clock for Linux and macOS. The target gives a program one call, which asks the kernel for a system call by name, `socket`, `bind`, `listen`, `accept`, `connect`, `getsockname`, `setsockopt`, `sendto`, `recvfrom`, `recvmsg`, `close`, `clock_gettime`, `nanosleep`, `kqueue`, `kevent`, `openat`, `read`, or `getrandom`, with at most six words, each an address or a 64-bit integer, and gives what the kernel gives, which is minus its error number when it refuses. On Linux that is the system call itself. On macOS it is the wrapper of `libSystem` of that name, which gives -1 and leaves the error number where `__error` says, and the target gives minus that number, so the caller reads both alike; the wrappers are imported only by a program that carries `net` or `time`, and the C library behind them is never called. On Windows it is the function of `ws2_32.dll` of that name, `closesocket` for `close`, which gives -1 and says why to `WSAGetLastError`, and the target gives minus that number, so the caller reads it as it reads the others; only the socket functions are called, which are `WSAStartup`, `WSAGetLastError`, `socket`, `bind`, `listen`, `accept`, `connect`, `getsockname`, `setsockopt`, `sendto`, `recvfrom`, and `closesocket`, and the library is in the executable's records for the loader only when the program carries `net`, so that a program that does not builds to the bytes it built to. The program calls `WSAStartup` once, before `main`, and only when it carries `net`. `openat` and `read`, which read the two files that the lookup of a host name reads, and `getrandom`, which fills the ids of its queries, are Linux's, and on macOS and Windows they give minus 38 as `epoll` does, so a program that only listens has none of them. A thirteenth number is not a call and says which kernel the program is built for, 0 for Linux, 1 for macOS, and 2 for Windows, as the family of an address, an option, a flag, an error number, and the first bytes of an address are the kernel's own, and `std/net.smith` writes each as the kernel it is built for reads it. The call is asked once, so a caller that is interrupted asks again. Everything else is written in Smith: `std/net.smith` and `std/time.smith` lay out the addresses, build each `Result` and `NetError` from the number, and answer each operation the target answers, through the compiler's own `__system`, `__reserve`, `__sized`, and `__consume`, which only the library may call. A server that cannot listen ends the program as a write the system refuses does: `std/http.smith` calls `__eprint`, which writes a line to standard error, and `__end`, which ends the program with a status, which the prelude called for `main` and the library may call too, and a call of `__eprint` in the library needs no `console`. A program that carries `time` for Windows, or `net` or `time` for WebAssembly, is refused with one message that names the target. Every call waits on Windows, and a task that waits for a descriptor there is not built, which waits for an issue of its own, as it needs completion ports; looking up a host name, which is not built on any machine yet, will call `GetAddrInfoW` of `ws2_32.dll` there.
- **The calls of files are the same numbered calls on every kernel, and a program that carries `fs` is the only one that is built to make them.** `std/fs.smith` asks `__system` for `openat`, `read`, `pread`, `pwrite`, `write`, `lseek`, `fchmod`, and `close_file`, which is `close` on Linux and macOS and `CloseHandle` on Windows, where a socket and a file are closed by other functions. On Linux they are the system calls. On macOS they are the wrappers of `libSystem` of those names, imported, with the others, only by a program that asks for the files, and `openat` is given its mode on the stack on arm64, where this kernel passes the variadic arguments of a call there. On Windows each is a function of `KERNEL32.dll`, imported by such a program alone, after the ones that every program imports: `openat` is `CreateFileW` with the path as UTF-16 that `std/fs.smith` makes, the access, and the disposition, of an existing file or a new one that empties one that exists, and with the backup semantics that let a directory be opened and refused by the first read; `pread` and `pwrite` are `ReadFile` and `WriteFile` with an `OVERLAPPED` that holds the place; `read` and `write` leave it out; `lseek` from the end is `GetFileSizeEx`; `fchmod` gives 0, as a file has no mode. A call that refuses gives minus `GetLastError`, except a read that reaches the end of a file or of a pipe, which gives 0. A count is cut to a billion bytes, and the loops of `std/fs.smith` ask again for the rest. The kernel number, 12, is 2 for a Windows program that carries `fs`. The library reads each kernel's flags and error numbers by that number, so one source builds on all three, and a test of a file runs on each kind of machine.
- Nothing from the system is needed to build. The compiler writes the records that ask the loader for a library and its symbols, so it needs no SDK and can build for any target from any machine.

## Why builds are fast

- **Only what is reached is compiled.** A run costs what its roots use, not the size of the project or the standard library. This holds of the prelude too, and of what is read of it: its types and traits are read with every program, and an `impl` of it is lexed and parsed only when the program reaches its trait or a type it is for, as the item on the prelude's source says. A program that uses nothing the prelude defines reads no `impl`, and checks the body of none of its functions or implementations.
- **A module of the library costs what the program reaches of it.** A module of `std/` is not lexed or parsed whole. A scan finds where each of its items starts and ends, by the brackets, strings, and comments of its lines and not by lexing it, and reads the module's `use` lines, its traits, its effects with their operations, its `without` lines, and the few items the compiler finds by name. So every module of `std/` is scanned, and one that declares an effect or a `without` is no exception. A function that answers an operation of an effect by asking the kernel is read when the program reaches the operation, and not when the effect is read. A function that only wraps what the compiler builds is told by the last line of its text before it is lexed. A `without` for a type the program does not reach is not checked by that program. A function, a struct, an enum, or an `impl` is lexed and parsed when the program names it, by the name it is written as in the file, which the parser lists for the file that is built and which is read from each item read in turn. An `impl` is read when its trait is reached and every type it is for, but those its trait writes `out` for, is. So the cost of a module is its scan, which is one pass over its bytes, and the items the program reaches, and nothing grows with what is added to a module that nothing reaches. A module of a project is read whole, as an error in an item no program reaches is still its error. A test builds a module with 1, 10, and 100 times as many functions, types, and `impl`s that nothing reaches, and holds the program, what is allocated, and the comparisons of definitions and of copies to what they are for the first. What no program reaches is not checked by a program, so a program that lists one name of a module checks no more of it than what that name reaches, and the check of the whole library, which `tests/read_by_reach.rs` runs, reads every module of `std/` whole and reaches every item in it, and finds no error.
- **An `impl` that is not reached costs its head and no more.** An `impl` of a trait the program reaches, for a type the program does not reach, has its head checked, as a mistake in it is an error, and nothing in it is walked, checked, or lowered, nor is anything only it names reached, until the type is. One of the program's own is dead code, a warning at the `impl` as a function nothing calls has, and one of the library's is none. A generic function nothing calls is not reached. A call of a handler, `net(...) { ... }`, reaches the types its effect's operations write, since the handler's lambdas are given values of them that no name in the program may say, so an `impl` for such a type that a lambda calls is walked and checked, as one for a type the program names is. A test builds a program beside the same program with a long body in such an `impl`, and in such a function, and holds each stage after the first to what it allocates for a short one, and checking to the same comparisons.
- **Each stage does the same work for each line, however large the program.** A walk over the program looks a definition or a copy of a function up by its hash, never by a search of a list, so what a stage does grows with the program and not with its square. At 100 times the size of the lexer the whole build takes under 100 times the instructions it takes at one, and `check` under 105 times. A test builds a part of the lexer at 1, 10, and 100 copies and holds each stage to [what the Speed section says](#speed), by what it allocates and by how many times the checker compares a definition or a copy of a function with another, which a search makes in proportion to its length. The compiler's maps and sets of numbers and names are hashed by a multiply and a rotate, with no crate, and nothing it reports or builds is in the order of a map.
- **Bodies check independently.** Signatures are complete, so bodies are checked in parallel across every core.
- **Rules, not search.** Every optimization above is a fixed rule.
- **Proofs are checked, not found.**
- **No cache.** There is nothing to invalidate, download, or go stale.

## Platform layer

Each platform needs a small set of foreign bindings for a window, a GPU surface, input, and audio, all through the C calling convention. Bindings are generated and validated with Clang at development time, so Clang never ships with the compiler.

| Platform | Window and input | GPU | Linking |
| --- | --- | --- | --- |
| macOS, iOS | AppKit or UIKit through the Objective-C runtime's C functions | Metal | Dynamic to system libraries. iOS builds are ahead-of-time only |
| Linux | Wayland or X11 socket protocol | Vulkan | Static possible without a GPU |
| Windows | Win32 through system DLLs | Vulkan | Dynamic to system DLLs |
| Android | NDK native activity, JNI for the rest | Vulkan | Dynamic, plus a manifest |

`smith --watch` keeps the socket a program listens on from one run to the next, and nothing a program can see says so: no effect, no operation of `net`, no parameter of `listen`, and no flag a program reads.

- **Only a program that `smith --watch` builds can keep one.** The library `smith --watch` builds a run with is the standard library with `std.net` changed: three lines are put into `system_listen_on` and `system_accept`, and the functions of `bootstrap/src/net_watched.smith` follow the module. A program that `smith build`, `smith run`, or `smith <task>` builds is built with the module as it is in `std/net.smith`, so it is the same bytes as it was before this was built, for every target, and looks at nothing that is not its own. `smith --watch build` and `smith --watch check` write no program that keeps a socket either.
- **A run is started with a socket at descriptor 3, and only that kind of run looks at it.** `listen_on` writes `listen <host> <port>` to the socket and reads the answer with `recvmsg`, which gives the descriptor of the socket that `smith --watch` keeps for the address, made the first time it is asked for and given again to each run after it, or the system's error number when it cannot be made. A run that finds nothing at descriptor 3, as one started by hand is, listens as any program does. `accept` looks at the socket before it takes a connection and gives `.closed` once `smith --watch` has closed its end.
- **How a run is stopped.** `smith --watch` closes its end of the socket and makes a connection to each socket the run listens on, so that a run that waits in `accept` is woken, looks, and leaves the connection in the socket for the next run. It then waits up to ten seconds for the run to serve the connections it took and end, and kills it after that. A run that listens on nothing is killed at once.
- **What it adds to the compiler** is the kernel call `recvmsg`, which on macOS is imported only by a program that asks for it, so a program built any other way imports what it did, and `__address_of`, which gives the address of a list's bytes as a `Nat`, so that the library writes the message the call reads in its own bytes, laid out as each kernel's header says. Windows has none of this.

## Testing

The test suite is a few properties per layer and a small regression corpus, with almost no unit tests. Tests touch only the compiler's commands and semantic properties, so refactors do not break them.

For the parser, one generator walks the grammar and builds a random derivation tree, with shrinking. The tree is flattened to program text and also folded into the expected syntax tree, so no second parser is needed.

1. Parsing generated text gives the expected tree.
2. Formatting is idempotent and preserves every token.
3. Mutated input never crashes or hangs, and anything the parser accepts passes property 2.

The other layers use a second generator that builds well-typed programs.

- Specific cases live as `.smith` files with expected output beside them, updated by one command and reviewed as a diff. In the bootstrap compiler the command is `SMITH_UPDATE=1 cargo test cases`, run in `bootstrap/`.
- A generator draws every choice from the seed of the run, which is made from the commit that is checked out, so the cases differ from one commit to the next and are the same for one commit, and many runs cover more than one run could. - Tests run in-process and in parallel.

- **No test writes, in the test process, a file that it then runs.** The tests run on many threads of one process, and a thread that starts a program forks the whole process, so a child can hold a file another thread has open for writing, and running that file fails as busy. `tests/support/executable.rs` has another process make the file, by copying one or by `install` from bytes, and no test tries a run again because a file was busy.

- **The sweep shows what the tests catch.** `bootstrap/sweep/sweep.sh` makes small changes to the compiler's source, one at a time, and runs every test against each. `sh sweep/sweep.sh run` in `bootstrap/` runs it, with the changes in `bootstrap/sweep/changes`, which a hash of the file, the line, and the operator picks, and writes `bootstrap/sweep/results`; `sh sweep/sweep.sh report` says which changes each test alone catches. A change that every test passes, and a change that makes the tests hang, are what the sweep finds. It changes `bootstrap/src` only, so it says nothing of the tests of `.github` and `install.sh`. No test is removed on its evidence, as two tests that catch the same break would each catch nothing alone.
- A test states its expectation from the generator that built its input, never from a line or column written by hand, so adding a feature does not break it.

Every target passes the same tests, which take their targets from the target enum's own list of cases, so adding a case runs them over it and no test names a target. How `smith run` starts a program on a kind of machine is checked again by the next change that alters that machine's executables.
- **`compiler/` and `std/` count as the compiler.** A change to a file under either runs every job a change to `bootstrap/` runs: the tests of `bootstrap/tests` are the only thing that holds the compiler written in Smith to anything, and the library's source in `std/` is built into the compiler's executable.
- A change that touches no file under `bootstrap/`, `compiler/`, `std/`, or `.github/` and not `.gitattributes`, which sets the bytes of the test cases on checkout, or `install.sh`, which the tests run, such as one to `knowledge/` or `.agents/` alone, runs no job that builds the compiler. `.github/changed.sh` decides this.
- A job that builds nothing, `.github/check-status.sh`, runs for every change and fails when a page of `language/` other than `index.md` has no `status`, a `status` other than `built`, `partial`, or `planned`, or `partial` without `built`.
- A newer push to a pull request cancels the run for the older push.
- A machine may not be available. GitHub ends a job that waits about fifteen minutes for one as `cancelled`, with no step run, and nothing in the workflows sets that limit, so a job that never started is not a failure of the change. Each machine job that never started is started again, and again a second time, in the same run, and only then counts as failed. `.github/never-started.sh` decides this from the list of jobs and how each ended, so it is tested without GitHub. Whether to look for such a job never depends on the result GitHub gives the matrix of machine jobs, only on the run not having been cancelled. `ci` judges each kind of machine by its newest job, so the merge queue never removes a pull request for a wait, while a job that ran and failed, or was stopped while running, is never started again. It passes only when it has read the list of jobs and found, for every kind of machine the change needs, a newest job that succeeded: a list that could not be read, an empty one, a machine with no job, a job that names no machine, and a skipped place standing for a lost job all fail.
- The job named `ci` is the one check the repository requires. `.github/ci-result.sh` makes it succeed only when every other job succeeded or was skipped on purpose, and fail when any failed or was cancelled. Adding a job to the workflow means adding it to what `ci` needs, and changes no rule.

### Generated code

A pull request says which executables it changes, and no hash of an executable is kept in the repository, so a change to generated code rewrites no file that another change rewrites.

- The `decide` job of `ci` builds the compiler of the commit the pull request is based on and the compiler of the pull request, and `.github/hash-cases.sh` gives each the hash of the executable of every case for every target, read from the compiler's own list of targets. `.github/check-generated.sh` compares them and prints, for each target, the cases whose executable differs, which the job adds to the summary of the run. A case that only one compiler builds is not compared.
- **A pull request that changes the executable of a case says so.** Its description holds a line that is exactly `Changes generated code.`. When any executable differs and the description has no such line, `ci` fails. Such a pull request is one the lead runs alone, as the `lead-issue` skill says.
- **A target's executables have the same bytes whichever kind of machine builds them.** The same job keeps its hashes of the pull request's compiler as the file `case-hashes`, and every kind of machine that runs tests downloads it, builds each case for each target, and fails the run for any hash that differs. It is `SMITH_HASHES=<file> cargo test -- --group=machine` by hand. Machines run only when their executables changed, as above. That every target builds identical bytes twice is a test of the group that runs once.

### The standards a library follows

A module of the library that reads or writes what a standard defines is held to the published text of that standard, and the text is in the repository so that a test can read it.

- **`reference/rfc/` holds each RFC a module follows, as `www.rfc-editor.org` published it, unchanged,** with `SHA256SUMS` beside them. A file is added once, when the first module that follows it is written, and is never edited. It holds `rfc4648.txt` for `std.base64`, `rfc9110.txt` and `rfc9112.txt` for `std.http1`, `rfc9113.txt` and `rfc7541.txt` for `std.http2`, `rfc5280.txt` for `std.x509`, and `rfc7468.txt` for its `pem`.
- **`reference/jsonrpc/` holds the JSON-RPC 2.0 Specification** as its site serves it, unchanged, which `std.jsonrpc` is held to as a module is held to an RFC.
- **`reference/mcp/` holds the Model Context Protocol specification at the version `std.mcp` follows,** as its repository tagged it, unchanged, with its license: the schema of every message as `schema.json`, the examples of each message, and the pages of its prose. The schema is read by a test as a table is, each example is run as a test, and the pages are held by a ledger as an RFC's sections are.
- **The text is the source of truth in three ways.** A table the standard gives, such as the static table of HPACK, is checked against the text by a test that reads it from the file. An example the standard works through is run as a test, read from the file. And every sentence of the standard that holds MUST, MUST NOT, or SHALL, in the sections a module follows, is listed in a ledger beside the module's tests with the test that holds it or the reason it binds nothing the module does, and a test fails when a sentence of those sections is in no line of the ledger.
- **A rule written in prose is not generated.** The code that keeps it is written by hand and held by its test. A table is written by hand too until [build steps](language/build-steps.md) are built, and is then written by a build step that reads the file, with the same test left to check it.

## Speed

Smith's scalar code is meant to be as fast as C's. A set of programs is each written in Smith and in C, the C built at its compiler's highest level of optimization, and the run time of both is recorded with the [timings](#timings) after every merge. A pass or a change to a target is judged by what it does to those numbers. Where the fastest code and the smallest executable differ, the fastest is chosen: a small executable is still a goal, and it comes second. How fast the compiler builds counts as much as how fast its programs run: a pass is judged by both numbers together, and a report of one gives the other beside it. A transformation that keeps what a program means and makes it faster is wanted, whatever the source looks like, as a struct handed to a function and handed back is passed as only what the function reads and changes.

The harness in `measure/` times a loop that pushes to a list, the lexer in `compiler/lexer.smith`, `std.json` writing a list of structs and reading the text, and how fast the compiler builds. Run `sh measure/run.sh` to build the compiler and time all four, or `sh measure/run.sh push`, `lexer`, `json`, or `build` for one. For `json` it also builds the writer and the reader with `smith build --map`, runs each under `valgrind --tool=callgrind --dump-instr=yes`, puts each address the run counted in the run of the map that holds it, and prints the instructions for a byte that the work costs beyond the same program that does not do it, by the function each was written in and by line of the source, the twelve largest of each with their share. A run that no line wrote is named for the runtime piece or the function that holds it. `SMITH=<path>` times another compiler than the one in `bootstrap/target/release`. It uses the compiler as the crate `smith`, through a path to `bootstrap/`, and takes no source file of it by path, so the lexer it times is the one `smith::count_tokens` calls, which lexes and counts the tokens and does nothing else with them. It depends on nothing outside the repository. The `linux` job of `ci` builds it with `cargo build --release --locked` whenever it builds the compiler, and does not run it, as a time on a shared machine says nothing; a change to `measure/` runs that job like a change to `compiler/`.

- **`push` and `lexer`** print one line for each program, each implementation, and each size, 1 KB to 1 MB, with the time for each push or each byte. The Rust lexer is the one in `bootstrap/src/lexer.rs`. A run of an executable that takes more than 30 seconds is given up on and said so. The time of an executable is its least of five runs less the run of a twin that builds the same input and does nothing with it, and a program too quick to tell from the system starting it is repeated in the one executable.
- **The lexer for `wasm`** is part of `lexer`, and is printed when `node` is installed: the lexer as a module under `node` beside the same program as an executable of this machine, each lexing 256 KB 40 times in a run, so that the engine has optimized the module, with the size of each, the time for a byte of each, which prints the same number of tokens, and the time and the instructions of building each for `wasm` and for `linux_x64`. A module that runs in no more than one and a half times the native time, and a build of the module that takes no more instructions than the build of the executable, are what the target is held to; a time on a shared machine is a guide, and the instructions are the same on every run.
- **`json`** writes a list of 100,000 small structs with `to_json`, each of an `id`, a `count`, and an `on`, and prints, for the Smith program, for the same written by hand in Rust with no library and built with `rustc`, and for that built with `rustc -O`, the time to build, the size of the executable, and the time for a byte of the text. The time of the Smith program is its least of five runs less the run of a twin that builds the list and does not write it, and the Rust's is a whole run, with the start of the process. When `valgrind` is installed it also prints the instructions of each for a byte of the text. It then reads the text it wrote with `from_json` into a list of the same structs, and prints the same lines for the reading, beside a reader written by hand in Rust that names each field, checks each number, and says where the text is wrong, each less its twin that writes the text and does not read it.
- **`build`** prints, for `hello`, for the lexer, and for the lexer's functions repeated under other names to 10 and to 100 times its size, the time of `smith build`, its least of five runs, the lines for each second, and the time of each stage from `--timings`. It then builds the Rust lexer alone, as a program that reads its input and prints the number of tokens, with `rustc` and with `rustc -O`, and prints beside the Smith lexer's build the time to build each, the size of each executable, and the time each takes for a byte of the same input, 1 MB. When `valgrind` is installed it also prints the instructions of each build, and of each lexer for a byte of 64 KB, from `valgrind --tool=callgrind`. Instructions are the same on every run, and times on a shared machine differ by a tenth, so a change of less than that is judged by instructions. By hand, `valgrind --tool=callgrind smith build <file>` and `callgrind_annotate --inclusive=yes` give where a stage spends them.

**The stages stay in proportion to the program.** At 100 times the size of a program no stage allocates more than 150 times what it allocates at one, and each copy added between 10 and 100 costs a stage no more than half as much again as each copy added between 1 and 10. The same second limit holds for the comparisons the checker makes of a definition of the file, and of a copy of a function, with another: `smith::work` counts them, and a lookup in a list makes one for each place in it before the one it looks for, where a lookup by hash makes one or two. Neither is a time, so both are the same on every machine. A test builds a part of the lexer at 1, 10, and 100 copies and holds each stage to these limits. It keeps to part of the lexer so that it takes a tenth of a second, and `sh measure/run.sh build` is the whole.

## Timings

The time each step takes is measured from the first program, so a slowdown is seen in the change that causes it.

- `smith --timings build`, and `smith --timings run` and `smith --timings` of a task before the program runs, print to standard error one line for each stage in the order they run, then a line for the total. The stages are `lex`, `parse`, `check`, `inline`, `trim`, `thread`, `fold`, `common`, `remove`, `emit`, and `write`, which saves the executable. A build that fails lists the stages that ran, after its errors. The executable is the same with the flag and without it. `smith --timings check` prints the same, after what the check reports, and as nothing is built its stages end at `check`.
- A test run ends with the tests that took the most steps, as [Testing](#testing) says.
- Continuous integration prints both on every run.
- After every merge to `main`, the `timings` workflow adds one line to `history.csv` on the `timings` branch and changes no earlier line. Pull requests record nothing. The job is the only one that can write to the repository, and it writes only to that branch. `.github/record-timings.sh` makes the line, and `--header` prints the first line.
- The first line names the fields: `commit`, `date`, `compiler_build_ms`, `compiler_bytes` (the optimized executable), `test_ms`, `job_ms`, and `programs`. `programs` holds space-separated `<case>/<target>/<field>=<value>` entries, for each file in `bootstrap/tests/cases` that builds and each target the job's machine can build for. The fields are the five stages and `total` as `<stage>_ms`, and `bytes`, and `run_ms` only for the target the machine can run. The entries grow with the cases and targets, so the first line stays the same.
- `measure/hyper/run.sh` holds `listen` against `hyper` on `tokio` on Linux, with a client of the standard library for both: requests a second from 64 connections that each ask one after another, the resident memory for each of 1,000 connections held open and answered, the time to build, and the size of the executable. It is a crate of its own with its own `Cargo.lock`, and CI does not build it. When it was written, on the machine that wrote it, `listen` gave about 52,000 requests a second and 20 KB for a connection in an executable of 110 KB built in 0.15 s, and `hyper` gave about 141,000 and 11 KB in an executable of 1.4 MB built with its dependencies in 13 s.
- To trace a change for the worse, read `history.csv` on the `timings` branch, find the first line where a field jumped, and take its `commit`.

## The map of an executable

The compiler is a tool for agents, and an agent that makes a program faster must see where its cost goes. An executable holds no names and no table of lines, which keeps it small, so the compiler writes them beside it: `smith build --map` writes [the map](language/command-line.md#the-map), and the executable is the same to the byte with it and without it.

- **Each instruction of the scalar form holds the place in the source it was lowered from, and the function that place is written in.** Every pass keeps both: an instruction that takes the place of others holds the place of the first of them, and inlining keeps the callee's. A target gives each instruction it emits the place of the instruction of the form it emits it for.
- **The map is made by `emit` from what it has laid out,** so it costs a build without `--map` nothing but holding the places.
- **Code the compiler adds, which no function of a program was written for, is named for what it does:** `<start>` for what runs before `main`, and one name for each piece of the runtime, in angle brackets and with no type in it: `<copy>`, `<join>`, `<escape>`, `<equal>`, `<digits>`, `<decimal>`, `<shortest>`, `<float_text>`, `<exp>`, `<exp_fast>`, `<exp_exact>`, `<exp_series>`, `<exp_multiply>`, `<ln>`, `<ln_series>`, `<ln_reciprocal>`, `<sin>`, `<cos>`, `<trig_reduce>`, `<trig_series>`, `<push>`, `<grow>`, `<reserve>`, `<append>`, `<start_words>`, `<arguments>`, `<words>`, `<line>`, `<measure>`, `<fill>`, `<utf8>`, `<valid>`, `<check>`, and for the stacks that give functions room `<stack_take>`, `<stack_ready>`, and `<stack_entry>`. What a type is given is `<fmt[T]>`, `<repr[T]>`, `<eq[T]>`, `<ord[T]>`, `<hash[T]>`, `<convert[T]>`, `<serialize[T]>`, or `<deserialize[T]>`, with the type in the brackets. A function a test builds that has no name is `<functionN>` by its place.
- **The `fn` lines and the `at` lines are built.** A function of the scalar form holds its name: the module, a dot, and the name as written, with the types it is made for in brackets, as `std.list.push[Nat]`, and for a function of an `impl` the types the `impl` is for, as `prelude.fmt[u64]`. Lowering gives it, from the module each place of the file says, which is `main` for a file with no path. Two functions are equal when they do the same, whatever they are called, and so are two instructions, wherever they were written. A function the program reaches that is built in place has no `fn` line, as `print` is not a function and `main` is often inlined. The target tells `emit` where each function begins, and `emit` gives each its address as the executable asks to be loaded, its size to where the next begins, and the bytes of frame it takes of the stack, which for a call includes the return address. The first line is `<start>`, from the first byte of code to the first function, and the last function ends where the code does, before the tables and the texts the code reads. For a module the address is the place of the byte in the file, and the functions are the bodies of its code section, with `<allocate>`, `<exit>`, `<start>`, and `<status>` after them. The text of the map is made where it is written, so a build without `--map` holds the places and no more.
- **An instruction holds its place, which is a file, a line and a column, and the name of the function that place is written in.** Lowering gives each instruction the place of the statement or expression it lowers it for, a loop's head and its step included, and what follows an expression's parts is placed at the expression, not at its last part. The function is the one the code is written in, so the code of a call that is lowered in place has the callee's name and not the caller's, and the arguments are passed at the call. The code of the prelude has no line of its own, so what is lowered in place from it, as the `each` of a `loop`, is placed at the call or the loop it is for and written in the function that holds it. What no line wrote, which is the function's entry, the code of the runtime, and the calls that give functions their stacks, holds no line and the name of the piece or the function it is for. Every pass keeps the place: an instruction that takes the place of others holds the place of the first of them, so a constant that folding makes of a sum is where the sum was and a fused instruction is where its product was, and inlining keeps the callee's. A constant that a pass makes holds no place at all. A target notes, as it emits each instruction, where its code begins, and the `at` lines of a function are the runs of its code that have one place, from the first byte of the function to the last: the code before the first instruction, and the code a target writes where the function returns, which no instruction of the form holds, are runs of the function's own, a run has `-` for the place when no line wrote it, and the code of an instruction with no place at all is counted in the run before it. A function all of whose code is its own, as `<copy>` is, has no `at` lines; the code of a piece of the runtime that is built in a function is a run named for the piece, and only the function's own entry and exit are named for the function. The names of the files and of the functions are kept once for the process, and an instruction holds a number for each, so it takes 16 bytes.
- **`smith profile` is planned on the map, in two modes, and neither is designed yet.** The first says where the cost of a run goes, by function and by line. The second, built after [tasks](language/tasks.md), is causal, as the profiler Coz is: it says how much faster the whole program would be if one line were faster, by pausing every other task when that line runs and measuring how often a unit of work finishes, where a unit is by default one request answered. For a program of one task the two say the same, so the second waits for tasks.
- The map is this compiler's own form and no standard one. Symbol tables and debugging records inside the executable, which other tools read, are not built.

## Releases

Every merge to `main` that changes what the compiler does publishes a release on GitHub.

- The version comes from the subjects of the commits since the last release, and from nothing else. `.github/next-version.sh` works it out and can be run by hand. While the first number is 0, a commit marked breaking with `!`, or a `feat`, raises the second number and sets the third to 0, and otherwise a `fix` or a `perf` raises the third. The first release is `v0.1.0`.
- A merge is released only when one of its commits is a `feat`, a `fix`, or a `perf`. Merges of `docs`, `test`, `ci`, `refactor`, `build`, `chore`, and `revert` commits publish nothing.
- A release holds the optimized compiler for each of the six kinds of machine a target needs, named for its target, as in `smith-linux_x64` and `smith-windows_x64.exe`, and `SHA256SUMS`, the SHA-256 hash of each. Its notes list the subject of each commit since the last release.
- The Linux executables of a release, `smith-linux_x64` and `smith-linux_arm64`, are linked statically, so that they need no C library from the machine they run on, as the programs they compile need none, and do not pay to find one when they start. The build fails when `file` or `ldd` says one needs a shared library, or when one does not run `--version`, and build and run a hello program, in a container that holds no C library, or writes other bytes than the compiler linked dynamically does. macOS and Windows have no static C library to link, so their executables are linked as before.
- `smith --version` prints `smith` and the version the compiler was released as. A build that is not a release prints `smith dev`.
- After every merge to `main`, the `release` workflow works out the version, builds on each kind of machine, and publishes. Pull requests and the merge queue never run it, and nothing waits on it. Only the job that publishes can write to the repository. Running it again for a commit already in a release makes no second one and changes none.
- `install.sh`, at the root of the repository, installs the newest release on macOS or Linux with `curl -fsSL https://raw.githubusercontent.com/smith-ai-lab/smith-lang/main/install.sh | sh`. It takes the file for the machine from the newest release, checks it against that release's `SHA256SUMS`, and only then puts it in `~/.local/bin/smith`, replacing any earlier one. A machine no release file is for, a hash that does not match, and a download that fails each install nothing, leave an installed `smith` as it was, and exit with a non-zero status. It holds no version and no hash, so no release changes it, and it needs only `sh` and `curl` besides what macOS and Linux hold. When `~/.local/bin` is not on the `PATH` it ends by saying so and giving the line to add. The whole script is one group at the start of the file, so a script cut off part way, as when the connection drops, runs nothing and exits with a non-zero status. The tests run it against a release on disk. One further check, `.github/check-install.sh`, installs from the real newest release on each kind of macOS and Linux machine CI uses, and runs only when `install.sh` or that check changes.
- A machine may not be available. GitHub ends a build that waits about fifteen minutes for one as `cancelled`, with no step run, and nothing in the workflow sets that limit. The build of a target that never started is started again, and again a second time, in the same run, and the release is published only when the list of jobs was read and the newest build of every target succeeded. A build that ran and failed is not started again, and no release is made from fewer than six. A run that works out a version and does not publish it, because a build failed or for any other reason, is a failed run and says so; a run that succeeds has either published or had nothing to publish. A job that follows one that may be skipped on purpose has a condition of its own that says when it runs, because without one it is skipped whenever any job before it is. `.github/never-started.sh` decides this, as for [Testing](#testing). The same holds for when to look.
- Every published release is kept. None is deleted or replaced.
- A draft is a release that was created and not published, and it has no tag. A run that failed can leave one, and it is not a release: the run that plans its version deletes it and publishes the version, and a draft never stops a run from publishing. A published release of the planned version is left as it is.
- The last job of the run asks GitHub whether a published release of the planned version exists, and fails the run when none does, whatever the job that publishes reported.
- Once Smith compiles itself, each release is built by the release before it, and then by itself. The two results are the same byte for byte, as in [Bootstrap](#bootstrap).

Everything git holds is also on GitLab, at `gitlab.com/smith-ai-lab/smith-lang`, so that it survives if GitHub is unavailable.

- It never forces. If GitLab holds something GitHub does not, or the push fails for any reason, such as a key GitLab refuses, the workflow fails and says why.
- It signs in with the private key in the secret `GITLAB_MIRROR_KEY`, a deploy key of that one GitLab project, and trusts GitLab only by the host key in `.github/gitlab-known-hosts`. Only the job that pushes reads the secret, and it cannot write to this repository.

Every file of every release is also on GitLab, in the package registry of `gitlab.com/smith-ai-lab/smith-lang`, so that the compiler can be fetched when GitHub is unavailable.

- The files of the release `v0.5.0` are the package `smith` at version `0.5.0`, and anyone can download one without signing in, as in `https://gitlab.com/api/v4/projects/smith-ai-lab%2Fsmith-lang/packages/generic/smith/0.5.0/smith-linux_x64`. `SHA256SUMS` is among them, and each file has the hash GitHub's `SHA256SUMS` gives it.
- The `mirror-releases` workflow runs after the `release` workflow finishes, and can be started by hand, which copies every file of every release that GitLab lacks. Pull requests and the merge queue never run it, and nothing waits on it.
- A file already on GitLab is never uploaded again or changed. If its hash differs from GitHub's, the workflow fails and names the file. Which files to upload is decided by `.github/plan-uploads.sh` from two lists alone, so it is tested without GitLab or GitHub.
- Both lists are read whole, however many releases and files there are, and a list that cannot be read fails the run before anything is uploaded.
- Either list may be empty: an empty GitLab gets every file. When the run ends in success, GitLab held every file GitHub holds with the same hash, because the script reads GitLab's list again after uploading and fails, naming a file, when one is missing or differs.
- It signs in with the secret `GITLAB_PACKAGE_TOKEN`, a deploy token that may write to the project's package registry and nothing else. Only the job that copies reads it.

## Bootstrap

The first compiler is written in Rust with no dependencies. It is retired once Smith compiles itself, and until then its code is the measure: the port must match it byte for byte, so it is made fast before the port and not after.

The compiler is being rewritten in Smith in `compiler/`, one stage at a time, beginning with the lexer in `compiler/lexer.smith`. Each stage is held to the Rust compiler by a test in `bootstrap/tests` that runs both on the same input and compares what they print, and a release contains nothing from `compiler/`.

- **It implements only enough Smith to write a compiler:** functions, structs, enums, `match`, generics and traits, strings, lists, maps, files, arenas, `with`, and `try`, followed by contracts and the `arith` procedure. Arrays with `for`, differentiation, devices, and tasks are built afterwards, in Smith.
- **It grows one feature at a time, end to end.** Each step takes a feature from source text to a running executable on each target built so far, starting with a program that prints one line. A program that uses a feature not built yet gets an ordinary error, with a line and column, that says so. The test generators cover what the compiler accepts so far and grow with it.
- **A trait a type is given automatically has no source.** The `Fmt`, the `Repr`, and the `Eq` a type is given are each a function the compiler writes for each type a call from `main` needs it for, and `Repr` and `Eq` call those of each part. The `Convert` an enum is given is the function that makes its case, written for each type that is converted to it. The `Convert` between whole numbers is written in the prelude, one `impl` for each pair, and the type that is expected settles the type `convert` goes to. The `Serialize` a type is given, which `std.serialize` defines, is a function of the type and of the type of the writer, written for each pair a call from `main` needs. It calls the function of the writer's `Writer` for each shape of the value, in the order of its parts, and the `Serialize` of each part, which is a type's own `impl` when it has one, and a loop over the elements of a list that carries the writer, so that nothing is built between the value and the writer. A program that writes no value reaches none of it, and is the program it was. The `Deserialize` a type is given, which `std.deserialize` defines, is written the same way for each type and each reader: it asks the reader for each shape in the order of the type's parts, and the `Deserialize` of each part, which is a type's own `impl` when it has one. A struct is a loop that asks the reader for a field's name, compares it with the names of its own fields, and carries the reader with what has been read of each field and whether it has, so that a field left out is `.none`, its default, or the reader's `fail` with `missing`. A list is a loop that asks `more` and pushes what is read. A function of the reader that gives an error ends the read with it, and so does a number outside its type, through `fail`. - **`exp` is two functions of the scalar form, a fast one that says whether it is sure, and an exact one.** `<exp>` takes a float and the table of `2^(j / 64)` as program data, as `<float_text>` takes its tables, and gives the float nearest `e` to that power, the even one at a tie.   - **`<exp_fast>` is the strategy of Ziv, in arithmetic of floats of 64 bits.** A float of 32 is widened, which is exact. `x = N * ln2 / 64 + r` for the whole number `N` nearest `x * 64 / ln2`, `N = 64 m + j`, and `exp(x) = 2^m * 2^(j / 64) * (1 + u)` with `u = exp(r) - 1` and `|r| <= ln2 / 128 + 2^-44`. `r` is a pair of floats: `x - N * L1` is exact, where `L1` is `ln2 / 64` cut to 36 bits so that `N * L1` is, `N * L2` is taken with its rounding error by one fused instruction, `L2` being `ln2 / 64 - L1` as a float, and what is left, under 2^-82, is dropped. `u` is `r + r^2 / 2 + q` as a pair, with `r^2` and its error by one fused instruction, and `q = r^3 * P(r)` by Horner's rule through `r^8`; the table holds `2^(j / 64)` as `th + tl` within 2^-107, and the result is `th + th * u + tl * (1 + u)`, summed with the errors of each sum and product, as `rhi + rlo` with `rhi` the float nearest the sum. The bound is: `r` within 2^-82, the cut of the series 2^-86, `q` 2^-75.8, the sums of `u` 2^-76.1, the sums of the result 2^-75.1, so the relative error of `rhi + rlo` is at most 2^-73.9; a Python model of the same steps, held to a decimal exponential on 300,000 floats, gave at worst 2^-75.55. `E` is 2^-72 for a float of 64 and 2^-71 for one of 32, and the nearest float is `rhi` when `rlo + E * rhi` is below half a unit in the last place of `rhi` and `rlo - E * rhi` is above minus half of it (a quarter below a power of 2), both strictly. For a float of 32, `rhi` is rounded to 32 bits first and the same test is made with its difference from `rhi` and `rlo`. A float that is not a number, is out of the range where the result is a normal number of the size (-700 to 700, -86 to 88), or fails the test, is left to the exact function; no table address is read out of the table, as `j` is below 64.
  - **`<exp_exact>` is right for every float.** It takes the bits of a float, so an `f32` is its 32 bits, and gives the bits of the float nearest `e` to that power, the even one at a tie. Past the numbers that give an infinity or 0 it answers without working, and a number whose magnitude is below 2^-54 (`f64`) or 2^-25 (`f32`) gives 1. Otherwise it holds the number as 256 bits of fixed point with 240 after the point, adds 1100 times `ln 2` so that it is positive, divides by `ln 2` for the power of 2 and the remainder `r`, sums the series of `exp(r / 64)` to 24 terms in `<exp_series>`, squares it six times with `<exp_multiply>` (the product of two 256-bit numbers, `MulHighU` of 32-bit words held in 64), and rounds once, to a subnormal where the power says so. It uses a float instruction only for the first guess of the quotient by `ln 2` (an add, a multiply, a conversion to a whole number, and the comparisons that find the numbers too great or too small), which the steps in fixed point after it correct by at most one, so the result does not depend on the guess. The error is under 2^-228, far below the 2^-120 that the worst cases that are known need, so one pass is always the right rounding. Every product and every division by a whole number rounds down, by under 1 in the last place (2^-240), and `r / 64` is under `ln 2 / 64`, which is under 0.01084. The first term is exact, and each of the 23 after it loses under `1 + 1/n` places, so the sum is low by under 26 places, whatever the term after the last, under 2^-247, adds. Squaring a number `y` turns a shortfall `e` into `2 y e` and loses under 1 place, and `y` is under `e^0.01084`, so six squarings turn the 26 places into under 127.2 times that, 3307, and add under 119 for their own roundings: under 3426 places, which is under 2^-228.2. The bound is held to every run by the test of `<exp_series>` at the greatest `r / 64`, at 0, and at the input that a bound of 2^-229 failed on, besides the inputs a seed draws.

No analysis of which names can read it is needed, because the checker refuses a use of a list after it was given away, and a list is duplicated only by `copy`, a function of `std.list` that pushes each element to a new list. A text, a slice, a literal, and `[]` have no room beyond their size. The memory is taken as a text's is, as [Text built at run time](#text-built-at-run-time-lives-in-memory-asked-of-the-system) says.
- **A slice is two values in the scalar form:** the address of its elements and its size, held as a text's are. `freeze` of a list is its first two values and no instruction, so a list that is frozen is not copied, and the room the list had is dropped. `s[a..b]` is the address of element `a`, which is the address of `s` with `a` times the size of an element added, and `b - a` for its size, so a piece asks for no memory and copies nothing, and `s[..k]` is the address of `s` and `k`. What a program knows of the size of a piece is `b - a`, so a piece of a piece is proven inside as a piece of a slice is. A slice given to a parameter of type `List[T]` that is not taken is passed as a text is, with its size again as the room. A slice written out is a run of bytes in the program's data, each element in the width of its type, found where the bytes of a text are, so the function that holds it asks for no memory and has no `alloc`; the elements of such a slice are numbers written out, and any other element is not built yet. The checker refuses a slice where a parameter takes a list, because the callee may grow it, and `push` of a slice.
- **The standard library starts inside the compiler.** Until the bootstrap compiler can compile the library's own source, it supplies what a program uses from it, beginning with `print` and the `console` effect. `Option`, `Result`, `bool`, `Order`, the `Fmt` trait with its implementation for `str`, the `Repr`, `Eq`, and `Ord` traits, the `Wrapping` trait, its implementations for every integer type, which call functions the compiler builds and only the prelude may call, the `Exit` trait with its implementations for `()` and for `Result`, and the `Try` trait, which has the one function `split`, with its implementations for `Result`, `Option`, and `Flow`, and `Flow` with its two type parameters, are Smith source in `std/prelude.smith` that the compiler reads as the next item says, and a program reaches them only through its own code, so they cost a program that never uses them nothing.
- **The prelude's source is a file that is divided when the compiler is built, and an `impl` of it is read when a program reaches it.** `std/prelude.smith` is the whole of the prelude's source, written out, each `impl` for each whole number type as it stands, and nothing writes it: no code prints Smith. It is not a module, so no `use` names it. `build.rs` divides it into its items, as it holds `std/`, by the lines an item starts and ends at, and records for each `impl` the trait and every name in the types it is for and in its generics, so that at run time an `impl` is found by those names and no item is lexed to find it. The types and traits are read with every program, as the checker finds `bool`, `Order`, `Option`, `Result`, and the traits `Fmt`, `Repr`, `Eq`, `Ord`, `Hash`, `Convert`, and `Exit` by name wherever the syntax means them, and a name the prelude defines is refused to a file, so these cost the same for every program. The traits of operations on whole numbers that a program calls by name, `Wrapping`, `Bits`, and `Float`, are not: each is divided from the rest, and is read only for a program that writes its name or the name of one of its functions, or imports a module of the standard library that does, a table that `build.rs` makes from the text of each module. A program that names none of them lexes and parses none of them, and a line added to one costs the programs that call for it, as a line added to a module of the library does. An `impl` is read when what the program reaches reaches its trait, or a type it is for, which is what reaching an item means for any `impl`: the first pass finds what `main` reaches among the items read, also in the `requires` and `ensures` of each function, as `by <= 30` reaches `Ord`, reads the `impl`s that this reaches, and finds again what they reach, until none is left. What is read is parsed once in a process and shared, an `impl` at a time, so a process that checks many programs reads each once. What a program reaches, and the program the checker gives, are those of the prelude read whole.
- **The library's source lives in `std/`, at the root of the repository, and the compiler holds it inside its executable.** One file is one module, and the file's name is the module's, so `std/list.smith` is `std.list`. `build.rs` writes a function that gives a module's source by its name, from the files it finds in `std/`, so the executable needs no file beside it and looking a module up costs the same however many there are. A `use` names a module, and only then is its file read, for the names it writes with `pub`, as the item about what a program reaches of a module says, so a build costs what the program reaches of the modules it imports. A function the compiler builds is written in its module as Smith source whose body calls the function the compiler builds under a name that starts with two underscores, as `push` calls `__push`, and a call of an imported name stays the call it was, so the executable is the one built without the `use`. A module's other items are compiled, and they are the program's own as far as the compiler can tell. When a program imports from a module, the module's items are put among the file's, as if they were written in it, after the file's own, those of the standard library when the program reaches them, and what the program does not reach is not checked or built, so an error in a function nothing reaches stops nothing and an import that is not called changes no executable. Every name of the module that the program does not list is the module's own: it is written with the module after it, as `helper@std.ascii`, in every place the module writes it, so it is not the name of anything in the file or in another module, and a program cannot write it. A name the program lists, and the functions of a trait it lists, keep their names. A module's function may call the module's own names and the functions the compiler builds, which only the prelude and a module may call. An error in a module's item is reported with the module's name and the line and column in its file. The compiler does not take an item from a module when it builds that item itself: a function whose whole body is a call of a function the compiler builds with its own parameters, in order, as `push` is, and a type or a trait the prelude defines. Items of a module are put among the file's after `use` has checked the list, and a module's own `use` lines are read as the file's are. `std/console.smith` declares the effect `console` with `print` as its operation, and a call of `print` is built by the compiler from a table of the operations the target provides. A name the compiler supplies is in scope with or without its `use` until it is an error to leave it out.

- **A project's module is found by its path, and read when a `use` names it.** The root is the folder the command ran in, and the module `db.transaction` is the file `db/transaction.smith` below it, so a `use` finds its file by its name and nothing scans the folder. The compiler is given the root and asks it for the module a `use` names, so a module of `std` is never a file, and only the files a `use` reaches are read, each once, however many files import it. A module's own `use` lines are read as it is read, and a `use` of a module that is still being read is a ring of imports that no order builds: one error at that `use`, that names the modules in the ring. The file that is built is not a module that others import from. A module's items are put among the file's as the library's are. Every name of the module is renamed `name@db.transaction`, except the names the built file lists, which are written as the file writes them, `begin as start` as `start`, and a module that lists a name of another writes it as that module does, so a private name is the name of nothing outside its module and two modules may each have a `helper`. A module a file imports itself is not a name the checker knows: the parser reads `transaction.begin` after `use db.transaction` as the one name `begin@db.transaction`, and in a module that is spliced the renaming writes the name the module gives `begin` in its place, so nothing in the executable says how a name was written. A function of a trait is written `Area.size`, and the trait's functions keep the module after them unless the built file lists them, so a call finds a trait's function by the name its module wrote, and a call of a function that two traits the file can name both have, written without a trait, is the error that says to write the trait. A function written in an `impl` is the function of its trait that has the same name as its module wrote it, whether or not the file lists that function, so the `impl` in the file that is built, which writes `show`, finds `show@ui.animation`, and an error about it names `show`. A name is not renamed after a `.`, nor where a `:` follows it unless it is a parameter, so a field and a named argument are written as the module that defines them wrote them. A field not written with `pub` is private to its module in a project: reading it, assigning it, or building the struct by a call, in another module, is an error at its place; a field of a struct of the library is private in the same way, and the prelude's structs have no private field. An `impl` is not imported: it is found wherever its trait or its type is reached, and is an error in a module that defines neither the trait nor any type it is for. A module's number gives the lines its tokens are at, so an error is at its place in its file and names the file's path. `smith check` with no file named reads each file of the folder that no `use` reached, and says what its syntax and its `use` lines say, though a build never reads it.
- **A module that has items with whole number parameters, or uses those of another module, is read whole, with the copies of them it is asked for.** [A whole number of an item of another module](language/inference.md#a-whole-number-of-an-item-of-another-module) is built by `values.rs` before the file is parsed, as it is for one file: the file that is built and each module that has such an item or takes one are lexed, with the modules they use looked for by their names in the source, so a module that has none and takes none is not lexed for it. The copy of an item for some numbers is made among the tokens of the module that has the item, and not of the file that asks for it, so it reads the names the module keeps to itself, and the `use` line of the file takes the copies in place of the item. The checker reads such a module as it reads any other, and the pass says again which copies are asked for until no more are, as it does for a file that has the items itself. An error in a copy is put back at the item's place in its module, with the numbers it was found for.
- **The words a program is started with are given only to a `main` that takes them.** A `main` with no parameter is compiled as it always was, and its executable asks the system for nothing about how it was started. A `main` with the parameter `args: List[str]` is called by a function of the runtime, written once in the scalar form, whose three parameters are what the system gives, the same on every target: a number, the address of that many addresses of texts, and the address of a command line. Linux and macOS give the number and the addresses, as the kernel and the loader start a program, and Windows gives the command line with the number all ones, from `GetCommandLineW`, another thin wrapper over the kernel. The runtime makes the list of the words after the program's name. For the system's words each is the system's own text, kept where it is, and for Windows the command line is split by the rules of the C runtime of Windows, with its units of UTF-16 written as UTF-8, so every target gives the same words. Memory is asked of the system only when there is a word. Each word is checked to be valid UTF-8 before `main` runs, by a function of the runtime that, for the first that is not, writes `argument N is not valid UTF-8` and a line break to standard error, where N counts from 1, and ends the program with status 1. The scalar form has a call into the system that ends the program with the status it is given, a byte, and a stream for standard error.
- **What `main` returns is turned into the status by a function of the prelude.** A `main` that returns nothing is where the program starts, and its executable is as it always was. A `main` that returns a type is called by a function the compiler adds to the prelude, which gives what `main` returns to the `exit` of that type's `Exit` and ends the program with the byte it gives, through the call into the system that ends the program. The function takes the words when `main` does, and lists the effects `main` lists and the two that `Exit` lists, `console` and `alloc`. A `main` whose type has no `Exit` is refused where its return type is written, and the error names the type and `Exit`. The `Exit` of a `Result` writes the failure to standard error, with a line break, through a function that only the prelude calls, as `__decimal` is.
- **Text built at run time lives in memory asked of the system.** The system is asked in pieces, and each list and each text takes its room from a stack of them, as [A handler's state is passed, and never global](#effects) says of the handler of `alloc`. A piece is 64 KB, or the number of bytes a request needs, with the 16 bytes at the end of the piece, rounded up to a multiple of 64 KB when that is more, except that a request which no piece of 64 KB has room for is given a piece with room for twice as many bytes. A list of that size that is the last memory its stack gave, and doubles, finds the room it lacks in the same piece and is not copied. The doubling after that finds none, and the list is copied into a piece of its own that has room for it to double, so a list that grows from one piece to any size is copied at every second doubling, and the memory it is copied from, which is not given back, is a third of the memory it ends with. The room beyond the request costs address space and nothing else, and no program can see it, since the system gives a page when it is first written and room that is never written is never given. On Linux and macOS `mmap` gives pages of zeros, and none is held by the program until it is written. On Windows `VirtualAlloc` is asked to reserve and commit the piece at once, so the commit charge of the program, which is what the system sets aside against its memory and its paging file, counts the room, and the memory the program holds does not, as a page is brought in when it is first written. A WebAssembly module grows its memory by the pages the piece needs, which the engine gives as pages of zeros and brings in when they are written, and a request of 2^31 bytes or more, which now has a piece of 2^32 bytes or more, ends the task as a request the engine refuses does. A request is rounded up to a multiple of 8, so that every address is one. A request that fits the bytes the stack has left takes them with a compare, an add, and a subtraction on the state, and calls nothing. One that does not fit goes to the piece that follows, when there is one that has room, and otherwise asks the system for a new piece, through the boundary [Standing alone](#standing-alone) names: `mmap` on Linux and macOS, and `VirtualAlloc` on Windows. A piece ends with the number of bytes it holds for the program and the address of the end of the piece after it, or nothing, so that a stack that is at the end of a piece finds the next from where it stands. A new piece is put between the piece the stack was in and the one that followed it. What was left of the old piece is not used again until the stack is back at its start, and nothing is given back to the system while the program runs, so all of it is freed when the program ends. A request the system refuses ends the task that made it with the failure `out_of_memory`, and the program with a failing status when that task is `main`, as [How a task ends](language/task-ending.md) says, having printed what came before, since the first request is made when the program first needs room. In a program with no group the program is the one task. A program that builds no text and no list at run time never asks, has no state to pass, and its executable does not import the call.
- **Two kinds of memory, by who owns a value.** This is planned, and the item after this one says what is built. The line between them is ownership, and never size.
  - **A value that is shared and cannot change is in the stacks.** A `str`, a `Slice`, and every value with `Copy` is never changed where it lies, since a `mut` that holds one is given a new value, so its memory never grows and never moves. Any number of names share it, taking its room is one addition, and it is released with everything else of its region, when the function or the round of a loop ends. A function's result is built in its caller's memory, as the item after this one says, and that is unchanged.
  - **A value that one name owns has memory of its own, for as long as its owner lives.** A `List` has one owner and is never copied without a word, so the compiler knows where each one grows and where each one dies, with no count kept and nothing collected. Its memory is given back exactly where its owner dies, and what its growing leaves is given back where it grows.
  - **One allocator serves every owned value, and asks the system only when it has nothing to give.** A list doubles, so its memory comes in sizes that are powers of two, and the allocator keeps, for each size, a list of the blocks that were given back. Taking a block is taking the first of that list, and giving one back is putting it first, a few instructions each, so a block a dead list leaves is the next one a new list of that size is given. When a list is empty the allocator takes a large piece from the system and cuts it. Its state is passed as the state of the handler of `alloc` is, and is never global. Which sizes it keeps lists for, and how it asks the system for the largest, is the allocator's own business and no rule of the language.
  - **The largest blocks grow where they are.** A block too large for the lists is a run of addresses reserved from the system, longer than it needs, of which only the pages it uses are touched, as an address that is never touched costs no memory. Growing it copies nothing, and the whole run goes back to the system when its owner dies. A target with no addresses to spare, as a WebAssembly module of 32 bits, grows by copying, and this section says what each target does when it is built.
  - **`freeze` hands a list's memory to the region.** A `List` that is frozen is a `Slice`, which is shared, so its memory no longer has one owner. Nothing is copied: the block joins the stacks of the region the slice lives in and is released with it.
  - No program can see any of this but in how much memory it holds.
- **Memory a function gives back.** A function's temporaries are released when it returns, and its result is built in its caller's memory, so nothing is copied on return, as [What a function leaves behind](language/arenas.md#what-a-function-leaves-behind) says. The memory is two stacks, and a function works with the pair of each that it uses, which are the first parameters of a function that asks for room, the source not showing them.
  - **Which stack a request is for is decided from the function alone.** Two values of a function are in one group when memory that one is or holds can be reached through the other: an address and the address moved from it, an address and what is loaded from it or stored at it, a value and the parameter of a block it jumps to, and every address a call takes or gives. A word of 8 bytes that is no address is taken for one where it moves through memory, as a copy of a list's elements moves an address. A request is for the stack of results when its address is in a group with an address the function returns, and for the stack of temporaries otherwise. The test errs towards the stack of results, so what it releases is never read after.
  - **A call is given the stacks as they are or swapped.** A call with an address in a group with one the caller returns is given the caller's pair of results and pair of temporaries as they are. Any other call is given them swapped: the callee's results are built in the caller's stack of temporaries, and the callee's temporaries lie in the caller's stack of results. A function gives back the pair for its results, moved on by what it wrote there. The caller's pair for its temporaries is the one it had before the call, and that is the whole of releasing: no instruction runs for it.
  - **Why nothing in use is overwritten.** Every stack a function is given has what is alive below where its free memory begins, and nothing alive above. A function writes only at and above that place, in the stack of results for its result and in the stack of temporaries for the rest, and gives back the first moved on by what it wrote. So it is enough to see that this holds for what a call gives and leaves, in the three ways a call can be.
    - **A callee whose result is the caller's temporary** is given the caller's stack of temporaries for its result and the caller's stack of results for its temporaries. It writes its result above what the caller has in the first, which the caller goes on with, moved on. It writes its temporaries above what the caller has in the second, and the caller goes on with the values it had, so the next thing it writes there goes over them. Nothing the caller or its caller has is in either place.
    - **A callee whose result the caller returns** is given both as they are. Its result is written above the caller's result so far, in the stack the caller gives back, and its temporaries above the caller's temporaries, which the caller goes on from as they were.
    - **Either of these calling a third function** is the same, with the callee in the place of the caller: the two stacks it was given have what is alive below and nothing above, as the caller's have, and it gives them on as they are or swapped. The third function leaves in the stack the callee gets back only its result, which the callee is about to use or return, and in the other only what is dead.
  - **A stack that has no piece cannot remember one,** and the pair a callee does not give back would lose the piece the callee takes. So the function the program starts with, before each call of a function that uses temporaries, makes each stack it passes have a piece, taking 8 bytes of a new one when it has none. Every stack below it has one, and a piece a callee takes for temporaries is the piece the next call takes, so the requests to the system stay as many as the most memory the program holds at once needs, however many calls it makes.
  - **A function takes only the pairs it uses.** A function that asks for nothing takes no pair. One whose every request is its result takes the pair for results, and gives it back. One that has temporaries takes the pair for temporaries too.
  - **A returned `mut` grown by `push` leaves its old buffers in the caller's memory** until the caller returns, since each buffer it grew out of is in the stack of results with the one it grew into.
  - **A round of a loop that hands nothing on releases what it took, as a call does when it returns.** A loop is a block that jumps to itself, and a round is the blocks from that block to a jump back to it. A round that hands nothing on ends by going back with the stack for temporaries that it began with, the pair the first block took as parameters, in place of the pair it has then, so that the stack is where the round found it. No instruction runs for it, and a loop whose rounds all do it hands the stack round as it is. Nothing is given back to the system: the next round takes the same memory again, as the next call of a function does. The stack for results is not touched, so what a round builds that its function returns stays.
    - **What a round hands on.** A value escapes a round when it is assigned to a name that lives past the round, which the first block takes as a parameter, when it is pushed or stored into something that does, when it is returned, when it is assigned to such a name before a `break`, which the blocks that leave the loop take, and when it is reachable from any of those. It is worked out from the function alone, with the groups of the item above: a round hands on when an address that it takes from the stack for temporaries, by a request or by a call whose result is built there, is in a group with a value that is made outside the loop or that the first block takes as a parameter. A group errs towards holding, so when in doubt it escapes, and a loop in which one address escapes releases none of its rounds.
    - **Why nothing in use is overwritten,** carried through for a round as it is for a call. The stack has, at the start of a round, what is alive below where its free memory begins and nothing above, since that holds where the loop is entered and, by what follows, where each round goes back. A round writes only at and above that place, in the stack for temporaries for what it takes from it and in the stack for results for what its callees keep for their temporaries and what it returns. What is alive when it goes back is what the next round and the code after the loop can read, which is the values of the parameters of the first block and what they hold, and the values made before the loop, which hold nothing made in the round since otherwise it escapes. All of that is below the place the round began at, or in the stack for results, which the round did not put back. So what the next round writes at and above that place overwrites nothing that is alive. The three ways a call can be, as above, hold in a round for the calls in it: a callee whose result the round only uses builds it in the stack the round is putting back, which is the round's own to put back, and a callee whose result the round returns builds it in the stack for results, which it does not.
    - **A stack that has no piece cannot remember one,** and a round that goes back to a stack that has none would ask the system for a piece in each round. So the function the program starts with, before a loop that releases its rounds, makes its stack for temporaries have a piece, as it does before a call, and every other function is given stacks that have one.
  - **An arena is a place in a function where the stack for temporaries is put back.** `with arena()` is the call of `alloc` with a body, which is lowered in place, between an instruction that opens the arena and one that closes it. Both are in the scalar form until the stacks of `alloc` are passed, and none is left after. When the stacks are passed, the opening takes the pair of the stack for temporaries as it is there and the closing goes on with that pair, as the end of a round does, so an arena costs no instruction whatever was taken in it, and none is left to run.
    - **What leaves the arena is built outside it.** A value made between the opening and the closing that is in a group, as the item above defines it, with a value made outside, is given back as a returned one is: it is built in the stack for results, which an arena does not put back. A group that has such a value errs towards holding, as a round does. The values of an arena that are in no such group lie in the stack for temporaries and are released at the closing, so a function whose every request is inside an arena asks for room only to pass it on, and a caller of it needs no more.
    - **The function the program starts with has a piece for the stack at the opening,** as before a loop that releases its rounds, since the memory taken above the pair is not remembered once the stack is put back.
    - **A `return` in the block leaves the block and not the function,** as in any lambda, so it ends at the closing. A `break` that would leave it is refused where the body is checked, as for any lambda.
- **Types depend on numbers first.** The bootstrap compiler lets a type mention a `Nat` and checks statements of arithmetic with `arith`. Statements about anything else, and proofs written out as functions, are built afterwards, in Smith. What the bootstrap compiler accepts is a part of that larger system and never a different one.
- **Contracts come before the port,** so that the compiler's own source, which is full of integer arithmetic, is the first real test of arithmetic that must be proven to fit.
- **The port is done by hand and checked by comparison.** The compiler is rewritten in Smith. For every program a generator produces, the Rust compiler and the Smith compiler must emit identical bytes.
- **The switch.** The Rust compiler builds the Smith compiler, that builds itself, and that builds itself again. The last two binaries must match byte for byte. Then the Rust compiler is deleted.

### Where each feature's code is

In `bootstrap/src/`, a feature of the language has a file of its own in each of the three stages that every feature changes, so work on it does not meet work on another. Whatever several features use stays in `parser.rs`, `check.rs`, and `check/to_scalar.rs`: the syntax tree's other nodes, type parameters and their scopes, the checker's `Defs`, `Checker`, and `Body`, and the lowering's `Out`, `Lowering`, and the lowering of expressions. A feature is moved just before work on it is due, so a feature not in the table is still in those three. Moving code changes nothing the compiler does.
